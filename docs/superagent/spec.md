# Super-agent 架构重建规格 v1

- 日期：2026-11-02。
- 状态：用于拆分实施票的行为规格；不代表功能已经实现。
- 已确认方向：以官方文章与原型为依据重建 DS Bot 核心，允许替换原有 Bot 调度架构。
- 已确认测试接口：Domain Engine 公开命令与查询为主要测试入口；来源、存储与设备执行补契约测试，再做真实 DSH 集成及 Windows 验收。

## Problem Statement

用户要一个持续存在的协作者：能在不同工作信道继续同一件事，并行推进独立工作，持续观察环境，在长期运行中恢复故障。用户不应承担底层会话选择、上下文搬运、后台作业轮询和重复派活的组织成本。

现有 DS Bot 以长期 Bot 身份、私聊和群会话组织工作。其工具、桌面和记忆能力有复用价值，但围绕消息与派活树的运行模型不足以直接承载完整 Super-agent。单纯增加连接器、子代理或任务看板也不能自动提供跨信道连续性、订阅直通、可恢复执行和跨设备常驻。

官方文章定义了连续、高效、主动、持久四个目标，以及双层架构、事件驱动、面向人的交互、计算/状态/环境分离、Watchdog 五个模块。官方原型已提供可借鉴的领域规则和执行机制，但其单仓库来源、单机存储、部署和权限假设需要适配，不能视为完整目标已经实现。

## Solution

建立一个基于 DSH 原生 agent loop 与 Session 的 Super-agent 运行核心。用户通过桌面、GitHub、飞书等熟悉的信道持续协作；Router 维护全局连续性、分派与对外交互，隔离 Worker 独立调查、执行和验证任务。后续环境事件按订阅直通对应工作，长操作异步完成，关键结果经统一规则与可靠通道交付。

同一核心支持单机常驻与服务器常驻。服务器运行计算，独立持久状态保障上下文和工作连续；用户真实设备保留工作环境，由受控 daemon 提供工具执行。独立 Watchdog 监督服务与任务进展。桌面是可断连的交互客户端，关闭界面不会等同于结束已授权工作。

完整交付以四项行为验收：

| 目标 | 用户能够观察的结果 |
| --- | --- |
| 连续 | 在一个信道提出要求，在另一个信道修正后，原工作采用最新有效方向；会话换代后仍能追溯原始依据 |
| 高效 | 两项独立工作并发；后台命令期间仍能受理输入、改变方向和停止；自动事件不会长期饿死人工输入 |
| 主动 | 明确规则允许系统提前调查、复现和准备交付；无价值或无需介入时安静，不因环境正文获得新权限 |
| 持久 | UI 关闭、Host 替换、设备断连后任务状态与未处理输入保持可核查，满足条件时继续，人工停止保持有效 |

## User Stories

1. 作为用户，我希望始终与同一个连续的 Super-agent 协作，以便不必管理底层 Session。
2. 作为用户，我希望同时提出多项独立工作，以便无需等上一件做完。
3. 作为用户，我希望在原信道收到与请求对应的确认和结果，以便知道哪件工作被受理和交付。
4. 作为用户，我希望在 GitHub 修改桌面发起工作的要求，以便无需复制整段背景。
5. 作为用户，我希望一句跟进到达原 Worker，以便系统不会重复创建同一项工作。
6. 作为用户，我希望无关的新要求能从旧任务中交回重派，以便原工作不被悄悄扩大。
7. 作为用户，我希望长命令期间继续提问或修正方向，以便后台执行不锁住对话。
8. 作为用户，我希望停止指令在重试和重启后仍然有效，以便自动机制不会恢复我已叫停的工作。
9. 作为用户，我希望普通讨论、感谢和重复 CI 不触发多余通知，以便注意力用于决定与验收。
10. 作为用户，我希望重要问题直接以明确的提问呈现，以便不会埋在日志或长报告里。
11. 作为用户，我希望问题回到提出相关要求的讨论位置，以便能就地回答。
12. 作为用户，我希望在等待我的某个决定时，其他已授权工作仍可进行，以便局部等待不会拖住整个系统。
13. 作为用户，我希望查看一项工作为什么开始、依据哪个请求，以便检查系统是否理解正确。
14. 作为用户，我希望查看原始事件、关键报告和验证证据，以便核查交付真实性。
15. 作为用户，我希望未完成草稿被明确标识，以便不会把创建 PR 当成已经完成。
16. 作为用户，我希望 PR 提交、等待评审和合并/关闭是不同状态，以便知道还需要做什么。
17. 作为用户，我希望自然结束的工作可以通过后续人类消息继续，以便修订不必丢失历史。
18. 作为用户，我希望相同请求的网络重试复用原结果，以便不会产生重复任务。
19. 作为用户，我希望在监督视图先看到需要我处理的事项，以便快速作决定。
20. 作为用户，我希望按需展开 Worker 执行记录，以便日常交互保持简洁且证据仍可查。
21. 作为用户，我希望会话压缩或换代保留原始历史入口，以便摘要遗漏可以补读。
22. 作为用户，我希望长内容可以完整续读，以便截断不会被误当作全文。
23. 作为用户，我希望系统沿事件、讨论、任务和交付物的关系召回背景，以便跨信道指代有依据。
24. 作为用户，我希望相似主题只成为查找候选，以便两件无关工作不会自动合并。
25. 作为用户，我希望关闭桌面界面后任务仍在常驻服务运行，以便界面生命周期不决定工作生命周期。
26. 作为用户，我希望重新连接后补读错过的结果，以便断网不导致交付丢失。
27. 作为用户，我希望个人设备离线时相关工作等待，以便系统不会在错误设备上重建不完整环境。
28. 作为用户，我希望设备重新上线后先核查现状再继续，以便不会重复执行结果未知的命令。
29. 作为用户，我希望文件、搜索、命令和输出来自同一执行环境，以便模型不会混用不同机器的状态。
30. 作为用户，我希望系统使用我的真实工具链和工作副本，以便未提交修改与硬件条件被正确保留。
31. 作为用户，我希望为设备限定可执行范围并撤销连接，以便持续接入有明确控制。
32. 作为用户，我希望私人与团队上下文分别隔离，以便一个范围的资料不会自动进入另一个范围。
33. 作为用户，我希望不同来源账号的同名用户和同编号资源互不混淆，以便不会串线或串权。
34. 作为用户，我希望凭据通过受控能力使用，以便来源正文和模型回复不需要包含密钥。
35. 作为用户，我希望旧团队历史保持可读，以便切换新核心后仍能查阅过去工作。
36. 作为用户，我希望迁移不自动重做旧派活，以便不会重复修改项目或发送消息。
37. 作为操作者，我希望为新请求配置明确的准入规则，以便无关来源不消耗研判与执行资源。
38. 作为操作者，我希望先观察主动规则会接哪些工作，以便在放开自动执行前检查误触发。
39. 作为操作者，我希望启用的规则能够实际提前复现或准备结果，以便主动性产生可用价值。
40. 作为操作者，我希望主动工作有资源预算和隔离目录，以便无价值尝试可以安静结束。
41. 作为操作者，我希望发布、合并、发送消息和本地准备分别受控，以便研究权限不会自动变成外部行动权限。
42. 作为操作者，我希望修改策略后旧研判被重新判断，以便过时的接单依据不会提交。
43. 作为操作者，我希望进行中的工作收到相关策略变化，以便可以在原有范围内正确处置。
44. 作为操作者，我希望暂停处理时来源仍记录事件，以便恢复后不会丢失环境变化。
45. 作为操作者，我希望暂停、停止和等待人工有不同语义，以便恢复动作可预测。
46. 作为操作者，我希望区分来源故障、消息投递失败和任务执行失败，以便选择正确的恢复动作。
47. 作为操作者，我希望短暂网络和模型故障有有界退避，以便偶发错误不需要反复手动介入。
48. 作为操作者，我希望永久失败和未知结果明确呈现，以便系统不会伪报成功或无限重试。
49. 作为操作者，我希望消息回执区分待发、已发和永久丢弃，以便知道用户是否实际收到结果。
50. 作为操作者，我希望发信重试由信道去重或对账，以便平台已收到但应答丢失时不刷屏。
51. 作为操作者，我希望提示词和策略可版本化回看，以便解释某次行为并安全调整配置。
52. 作为操作者，我希望设置并发和角色模型，以便合理分配响应速度、执行能力与成本。
53. 作为操作者，我希望独立监督器在主服务失效时仍可工作，以便故障不会同时停掉恢复机制。
54. 作为操作者，我希望监督器能发现假存活的循环与目标偏离，以便有进程不等于有实质进展。
55. 作为操作者，我希望监督器识别正常等待设备或用户，以便不会把合理等待当作故障。
56. 作为操作者，我希望监督动作有记录和预算，以便恢复机制本身不会失控。
57. 作为操作者，我希望在 Windows 原生运行常驻服务与客户端，以便不依赖 POSIX 运维脚本。
58. 作为操作者，我希望替换计算进程后仍能读取同一任务和 Session 状态，以便升级与恢复不破坏连续性。
59. 作为操作者，我希望旧 Host 和旧 Assignment 失去写入权限，以便恢复后不会有两个执行者同时提交。
60. 作为操作者，我希望分别观测业务状态与 Session 状态的持久化，以便一套成功不会掩盖另一套失败。
61. 作为 Router，我希望批量处理等待的候选，以便突发事件不会要求逐条重复往返。
62. 作为 Router，我希望已订阅的跟进直通 Worker，并收到必要通知，以便保持全局可见且减少转发负担。
63. 作为 Router，我希望收到简短报告和可续读引用，以便保持上下文预算。
64. 作为 Worker，我希望读到原始请求与上下文依据，以便不把路由摘要当成技术规格。
65. 作为 Worker，我希望跟踪多个相关 Thread，以便同一工作可跨聊天、PR 和 CI 连续推进。
66. 作为 Worker，我希望将越界跟进交回 Router，以便不用自行获得新授权。
67. 作为 Worker，我希望后台命令与子代理完成时收到事件，以便无需轮询等待。
68. 作为 Worker，我希望重试通常保留原 Session 与目录，以便恢复已有调查和修改。
69. 作为 Worker，我希望重启后获得未读输入和恢复提示，以便先核查副作用再继续。
70. 作为 Worker，我希望在交给人验收时可保留明确的预览服务，以便人可以检查结果而不占用执行槽。
71. 作为维护者，我希望通过同一公开 Engine 接口验证领域规则，以便测试不绑定私有实现结构。
72. 作为维护者，我希望来源、存储和设备适配器遵循可复用契约，以便替换后保留行为。
73. 作为维护者，我希望来源 kind 与 instance 分开，以便增加仓库或账号不改变既有资源身份。
74. 作为维护者，我希望业务事务与外部副作用分开，以便故障恢复能解释哪些承诺已经提交。
75. 作为维护者，我希望保留可核查的来源和许可，以便移植官方原型代码符合项目要求。
76. 作为维护者，我希望单测、mock 集成、真实模型和原生验收分别报告，以便证据不会被夸大。

## Implementation Decisions

### D01. 运行核心与职责

- 新核心采用类型明确的 TypeScript 模块和 DSH bundle。模型执行继续走 DSH 原生 loop、工具与模型路由，不新增第二套模型运行时。
- 每个上下文共享实例初始只有一个逻辑 Router。采用单活动 Host 与可替换进程的部署方式；分片不是首个版本的前提。
- Router 处理接单、关联、跨任务事实与人类交互；Worker 负责技术调查、方案、实现与验证。路由转交原始请求及必要事实，不增加请求未包含的技术要求。
- Router 工具集保持有限并限制等待。Worker 工具按任务与执行环境配置，其内部子代理继承相应权限与生命周期。

### D02. 核心对象与状态归属

| 对象 | 规格定义与不变量 |
| --- | --- |
| Instance | 可以共享上下文的服务范围；不同实例互不共享底层上下文 |
| Source kind / instance | 可复用接入实现 / 一份账号、仓库或接收范围配置 |
| Trigger | 稳定 ID 的不可变事件；正文、引文与来源内容不会改变部署授权 |
| Thread | 来源定义的连续讨论流；首个关联 Thread 承载该事件的新请求 Eval |
| Correlation | 讨论之间的上下文关系，只辅助读取，不直接路由 |
| Subscription | Thread 与 Ticket 的多对多信息投递关系 |
| Policy | 版本化接单规则、模式和各来源实例的准入配置 |
| Eval / Decision | 对候选批次的研判 / 持久记录的决定 |
| Mandate | 接受工作时形成的不可变授权依据、范围、强度与策略版本 |
| Ticket | 持久的授权工作身份，独立于 Session 与某次执行 |
| Assignment | Ticket 与某次执行的绑定，可替换且有独立代次 |
| Input | 交给 Ticket 的事实，包括事件、恢复、策略变化和路由说明 |
| Report / Attention | 结构化执行状态与证据 / 等待人回答的明确问题 |
| Effect / Outbox | 提交后待执行的操作 / 受用途与地址约束的消息及回执 |
| Environment | 工具实际执行的设备、目录、能力与授权范围 |

### D03. 稳定标识与来源实例

- 所有持久对象属于明确的 Instance。来源配置区分 kind 和 instance，Trigger、Thread、Channel、Actor 和 Policy 来源部分均携带来源实例身份。
- GitHub 资源保留服务地址、仓库及原生资源身份，不能只用编号。编辑形成的新事件包含原生更新版本。
- 两个来源实例的相同编号或相同原生用户 ID 不共享消息、订阅或白名单权限。来源身份不自动跨平台映射为同一人。
- 关联依据保存来源引用与决定记录。搜索相似度只产生候选；建立整条 Thread 订阅需要显式引用或唯一且可核查的指代。
- 来源身份取自受信接收路径并核查资源范围；使用无歧义元组编码，正文不能自报来源或权限。逻辑来源对象跨编辑保持身份，Trigger 包含原生版本/事件类型；传输重试不生成新逻辑消息。
- 不可变事件与当前消息投影分开。可核查较新版本才能推进投影；同版本异文、不可比版本记录冲突或 unknown 并查证。删除形成有证据的 tombstone，迟到旧编辑不复活；删除不等于人工 stop，不自动撤销既有 Mandate，删除内容不能用于新的接单或关联。
- 跨信道关联另核查目标可访问性、同 Instance 和唯一目标，保留来源事件、目标及决定；引用不是新的读取、执行或发布权限。旧标识迁移需要部署配置证据和唯一的全限定目标，歧义保留待核查。

### D04. 入站与新任务研判

- 来源按稳定 ID 去重并核查接收范围，记录接收或过滤原因。排除来源自身消息，保留读取位置与恢复所需信息。
- 进入领域的事件先归入 Thread 并进行订阅 fan-out。无人拥有的新请求再进入主 Thread 的 Eval。
- 每个 Thread 同时最多一个 Eval，其间到达的候选进入下一批；不同 Thread 不被强行合成一项工作。
- Gate 确定新工作是否具备准入依据，语义层判断意图、范围与规则。明确请求可以直接批量路由，推断候选需要足够语义证据。
- 批次授权来源必须可追溯；其他消息只能补充上下文，不能借用批次中更强请求的身份扩大授权。
- Eval 超时从候选实际送达 Router 后计时，采用有界重新排队；耗尽后记录 unavailable，保留重评入口。

### D05. 订阅、消息归属与交回

- 一个 Ticket 可以订阅多个 Thread，一个 Thread 可以有多个 Ticket。匹配事件投递给相关工作，不因此获得新权限。
- 每条事件保留接收时的 fanout 和归属依据；后来增加订阅不能反向赋予既有消息所有权。显式 attach 通过新的决定记录该事件的承接。
- 自有 Thread 上的人类跟进由收到它的 Worker 判断；它可以处理范围内请求，也可以携原因 handback。所有拥有者交回后才重新 Eval。
- 跨信道的人类跟进回到原 Ticket、原 Worker 和原 Session，作为新的稳定 Input 进入历史并递增方向版本；来源信道变化不重新创建工作，也不扩大原 Mandate。
- 仍有拥有者时，Router 不重复 accept、attach、ignore 或 requeue；通过明确授权的 stop 是例外。
- context-only 订阅只提供背景，不获得跟进归属，不凭该讨论中的人类消息恢复 ended Ticket。
- 机器人或 CI 可作为已有工作的上下文，同时按独立候选规则研判，但不能冒充明确人类请求。
- handback 不把原工作变成新授权；不能立刻将消息 attach 回刚交回它的同一 Ticket。

### D06. 授权、策略变化与三种暂停

- Mandate 保留原始授权范围。范围外工作形成新决定和新授权，不能通过修改标题或路由说明扩大原授权。
- proactive 模式为 off、observe、auto。明确允许的人类请求在各模式均可处理；observe 只记录 would-accept，auto 才允许推断接单。
- 机器人最多产生推断候选。推断接单需命中启用规则，并记录完整研判与证据。
- Policy 变化使进行中的 Eval 失效重排，仅向受影响 live Ticket 发送变化说明，默认不强制取消全部任务。ended Ticket 恢复前重新验证 Mandate。
- 暂停处理时，来源继续记录，暂停新 Eval、派发、输入投递及外发消息；已有运行回合不因该开关自动中断，恢复后调整超时计时。
- 人工 stop 撤回该 Ticket 的继续执行授权，停止相关执行，保留历史；CI、后续普通消息与监督器不能自动恢复它。
- 人工 stop 是持久约束；只有用户明确恢复才创建新的 Assignment，并重新核验授权。Ticket、Session 历史和工作目录可以保留，设备重新上线不能解除 stop。
- 明确等待人工确认形成持久执行约束，跨跟进、Assignment 与重启保持，直到具备相应权限的人解除。

### D07. Ticket 与交付状态

- Ticket 的 open/ended、Assignment 的 pending/running/ended、Session 的上下文、turn 和 job 状态分别维护。Agent idle 不等于任务完成。
- Report 支持 progress、waiting、ready、blocked、failed、dropped。Attention 是结构化问题，不能从自由文本猜测。
- 用户可见执行状态至少区分 `running`、`waiting-human`、`waiting-device`、`unknown`、`stopped` 和 `ready`，并显示下一步由 Worker、用户、设备或对账流程推动。`waiting-device` 是正常等待；`unknown` 只暂停受影响工作及其依赖。
- 无待完成交付 Thread 的 ready 可结束为 completed。存在已绑定 PR 时，ready 表示可验收，还要跟踪本工作创建或跟随的交付 Thread 完成条件。
- PR 已关闭但有未完成的恢复或已承接跟进时，延迟结束，避免丢失新请求。多个 PR 依据原型的归属与完成规则计算。
- 自然 ended 的工作可因自有 Thread 上人类跟进恢复同一 Ticket，并重新校验授权；人工 stopped 的工作不自动恢复。
- blocked/failed 后自动事件保留但不自动继续执行；人的新输入、合法恢复报告或 retry 可按规则释放等待。
- `unknown` 先按原 command/job ID 做有界查证或向用户提出一次带证据的问题；在对账或用户决定前不盲目重做、换设备或扩大目标，无关工作继续。

### D08. 并发与全双工

- 并发槽覆盖任务目录准备、启动、唤醒、活跃回合，以及回合后仍运行的后台 jobs/subagents。
- 普通自动输入按正常槽等待；人的跟进或必要状态请求优先，并可使用一个有界额外槽，避免被新任务持续挤压。
- 长命令和子任务通过异步启动与取消执行，立即返回可追踪的启动事实，完成后以事件送回所属 Worker。
- 新输入在当前推理步结束后可以处理，不等待后台工具完成；不得把循环轮询实现为 Router 的常驻等待。
- Worker 交给人验收时释放槽并停止相关子代理，可留下明确归属的预览服务。它不占执行槽，完成也不自动唤醒 Worker。
- Assignment 结束时按归属清理 jobs/subagents；迟到结果不唤醒新 Assignment。后台工作具备有界等待和清理策略，不能无限占槽。

### D09. 输入投递与重启恢复

- Input 分别记录待投递、已投递和实际进入 Session 历史的事实。仅有 inbox claim 不足以认定已经读取。
- 投递使用稳定消息 ID，检查持久历史和待处理 inbox，经过 Session flush 后确认投递。
- retry/restart 创建新 Assignment，通常复用 Ticket 的 Session 与执行目录；恢复前清理待重投输入的旧副本。
- 已投递但未实际读取的输入可恢复；结束工作时未承接且未获有效处理的跟进重新交给领域规则处置。
- 新 Assignment 启动前协调旧执行停止。重启提示要求核查目录、版本控制与外部平台现状，不将未见结果的写操作盲目重做。
- 崩溃恢复不保证命令从原执行点续跑。结果未知是独立事实，需要幂等重试、对账或明确人工处置。
- 接管遵循 `Instance 协调行锁 → Host epoch/fencing token → Assignment 代次 → Session write epoch → Environment incarnation + device jobId` 的权威链；新 Host 先取得持久写权，再读取状态、对账设备与未知结果、结束旧 Assignment，最后创建带恢复说明的新 Assignment。
- 旧 Host、旧 Assignment、旧 Session handle 和旧设备回调即使迟到也只能形成 stale 审计事实；恢复只处理尚未进入 Session 的 Input，已入历史的 Input 按稳定 ID 去重，不承诺 shell、半个模型 turn 或设备命令续跑。

### D10. Effects、Outbox 与对外行为

- 领域状态和需要跨重启存活的 Effects 在同一业务事务提交；外部操作在提交后进行。失败事务不会留下已授权执行的排队操作。
- Effect 使用稳定键、不可复用行身份和 payload 代次标识一次尝试；同键更新保留排队位置，删除后重建取得新身份。成功删除、失败退避和延期均条件匹配这些身份，旧尝试不能清掉或改写新代操作。瞬时故障有界退避，永久错误或耗尽重试有可见记录。
- 持久入队是恢复依据，提交后 wake 仅为提示；启动与周期扫描补齐丢失通知。派发端只读取已提交意图，不能在事务内沿用同连接的 microtask 提前执行外部动作。
- 外发用途区分 acknowledgement、answer、result、attention。受控确认可由 Worker 请求，主要更新和结果由 Router 组织。
- answer 需对应原始人类问题及 Worker 可回答事实；attention 必须匹配当前结构化问题；result 由当前 ready，或 ended 的 completed、merged、dropped 结果支持，是否通知仍按沟通规则判断。
- 确认与回答回原消息；人工问题回引发它的消息，否则回工作发起处；交付保持原信道，变更目标需明确依据。
- 普通 progress 留在内部。Worker 的 PR 创建与评审处理属于执行交付，不能绕过聊天发送限制追加任意通知。
- Outbox 回执区分 pending、sent、dropped。临时关闭来源时等待，永久不可达或已不允许的目的地才终止并记录原因。
- 同任务同会话尽量保持确认先于结果，错误不能无限阻塞其他任务。平台已收到而响应丢失的窗口由 Channel 幂等键、marker 或查询对账处理。
- pending 不能被宣称已经收到；dropped 不自动改投其他对象。数据库事务本身不构成跨平台 exactly-once 保证。

### D11. 上下文、召回与长期连续性

- 对象卡片内联 ID、简短摘要和紧密关联信息；超预算内容保留原文与续读入口。每次读取返回下一跳关联和分页事实。
- Worker 阅读原始请求，Router 摘要不代替原始证据。Thread 邻近内容与引用关系用于减少往返，不能无限注入历史。
- Trigger、Thread、Ticket、Assignment、Report、交付物和 Session 历史构成可逐跳读取的引用关系。
- 压缩、缓存失效和 Session 换代保留原始证据。换代显式交接目标、约束、授权、未处理输入及关联入口，随后只由当前执行者继续。
- 引用召回与持久知识分别处理；不把这套机制宣称为已经解决跨月长期记忆质量。

### D12. 提示词与角色配置

- 提示词区分角色、团队沟通、工作范围、交付要求、来源技能、环境和 Policy。保留默认文本、覆盖来源、版本及升级差异。
- 保存基于明确 revision，冲突拒绝且保留草稿。每次模型请求记录所用版本，变更在请求边界生效，不通过重启偷偷切换语义。
- 提示词不能覆盖 Gate、Mandate、工具限制或来源身份。原型的具体仓库流程和自动合并条件按本项目规则配置。
- 角色可保留名称、模型、指令和技能；它不把新工作固定塞入某个长期 Bot 私聊。

### D13. 存储、事务与所有权

- 单机业务基线采用 SQLite；服务器共享业务状态采用 PostgreSQL。两者实现同一行为合约，新公开命令和存储接口异步化。
- DSH Session 采用公开持久化接口；服务器另实现满足其合约的共享后端。迁移业务库不等于迁移 Session 历史。
- 业务与 Session 状态用稳定消息 ID、flush、恢复扫描和对账衔接，不假设它们天然共享一个 ACID 事务。
- 单实例先使用一个活动 Host。计算替换前后，业务工作与 Session 都有明确写所有权、租约、epoch/fencing 和过期执行隔离；Instance 协调锁只证明业务写入顺序，不证明设备进程已停止。
- 旧 Host、旧 Assignment 的回调不能改变当前有效状态。共享存储故障时不能在未持久化授权的情况下继续派发新副作用。
- 采用显式异步事务上下文，领域规则和存储端口复用本次命令绑定的连接；领域状态、Effect 意图、Outbox 记录和命令回执同事务提交，等待所有操作完成后才 COMMIT。内部规则不自行开启嵌套顶层事务，也不使用跨 await 的共享 depth/current-transaction 字段。
- 同 Instance 的领域写命令串行化，跨聚合读取和写入保持同一事务；SQLite 以写锁保障，PostgreSQL 采用事务内 Instance 协调行锁；真实数据库最小实验已验证，同 Instance 所有写入口必须先锁预存协调行再读状态，多对象按稳定顺序取锁。事务内只允许有界数据库操作和确定性规则；模型、网络、设备及外发经提交后的 Effect 执行。
- 命令使用稳定 command ID、规范化输入指纹和持久回执去重。同 ID 不同输入拒绝；COMMIT 应答未知时用原 ID 在新连接对账，查不清保留 unknown，不换身份盲重试。生产输入编码和版本规则在存储切片落实。
- 提交对账在新 READ COMMITTED 事务先重新取得同 Instance 协调锁，再读取回执，避免暂时无记录与原提交竞争；存在即复用，锁后仍缺失才允许用原 ID 重算。40P01/40001 回滚后有界重跑整个事务，55P03 不冒充接受，其他错误按分类处理。事务中不执行外部副作用。
- 已完成原创小模型的 SQLite 异步事务协议实验；这不代表官方 Engine 的完整异步移植、完整 Outbox、PostgreSQL 或共享后端已验收。快照加 revision CAS 暂不作为总体基线，完整跨聚合读取集合与安全重算仍需额外证明。
- Session 后端必须实现已取得 handle 的 live 事件路由与 flush 屏障；append 应答不能代替 flush 的持久承诺。Host 替换按合法写权重新打开 Session，由原生 loop 修复中断 turn，不承诺半个 turn 或命令在原位置续跑。
- 固定版本的公开 Session replay 实验发现恢复构造期会产生未发布的 session/end-seed；适配器须覆盖已持久前缀到 live 事件之间的构造期记录。实验经公开 Query 取副本、补存并 flush 后 announce，生产集成保持原生 loop 生命周期。close 失败不释放写权，旧 handle 不自动重获；epoch 接管须有合法控制依据。

### D14. 设备执行与客户端接入

- 正式部署为常驻 Host、独立存储、桌面客户端和设备 daemon；本机可先承担常驻 Host，完整验收另覆盖服务器与第二台设备。
- daemon 保留真实环境和作业恢复记录，不持有模型会话历史。请求明确环境、工作目录、权限与所属执行代次。
- 文件读写、glob/grep、shell/PTY、输出读取和取消必须进入同一执行世界；附件、spill、技能发现和路径映射逐项遵循合约。
- 设备离线时按能力等待，重新连接后查询作业与现实结果再继续。取消有明确确认或未知状态，不能只取消 Host 的等待就宣称远端已停止。
- 设备与客户端分别认证、按 Instance/Environment 授权并支持撤销；传输受保护，原型 loopback 管理接口不直接作为公网客户端入口。
- 客户端断连不结束已授权工作，重连按游标补读并处理重复，撤销客户端权限不自动改变 Worker 的任务权限。
- MCP、浏览器和 Office 复用能力逐项声明运行位置；未通过远程合约的能力只标为本地可用。
- 内置搜索的 Host 打包可执行文件路径和路径处理不能直接假设在异构设备有效；能力组合必须验证 executable、cwd、搜索结果和文件目标的一致性。默认进程内后台 jobs 的日志可持久化，不代表 live 作业可跨 Host 重启自动恢复；设备作业需以稳定身份对账。

- 最小运行验证选定每 Worker 固定 Environment 的配套能力与独立 scope；targetKey 不用作进程路径，无 Host 映射时不猜共享路径。搜索优先由设备侧工具解析执行程序/cwd 并返回结构化相对路径，避免异构目标依赖 Host 打包程序与路径语义。
- 作业身份包含 Environment、daemon incarnation 和稳定 job ID；回执丢失先查询，输出按字节偏移非消费读取。cancel 先为 stopping，只有设备确认相同执行范围静止才标停止；身份不符或无法查明时保持 unknown，不盲重启。
- 已确认启动的设备 job 在原授权和设备本地时限内有界继续；Host 断连不等于设备停止。人工 stop 立即形成持久事实，设备离线时保持 `stopping`/`pending-device-confirmation`，只有同一 managed range 静止得到确认才可进入 `cancelled`；重新上线不能解除人工 stop。
- 接管或重连遇到未知副作用时，只阻止受影响操作及其依赖，保留 `unknown` 并向用户提出一次带证据的问题；未完成可靠对账或用户决定前，不自动重做、换设备或扩大目标。
- 已验证同平台本机双进程协议与 Cordis 查询/读取服务 scope 子集；完整同步 spawn handle、原生工具/Agent 继承、PTY/进程树、daemon 重启持久作业及真实异构设备仍须切片验收。未经验证的组合不启用，不回退到 Host 同名路径。

### D15. 主动工作与投机执行

- 主动行为由版本化规则说明触发条件、可执行范围、交付方式和预算。先支持 observe，再允许启用规则的实际 auto 执行。
- 沿用参考的 Policy、书面规则与提示词机制，不另立动作分级设置。已授权动作直接推进，超出范围才提问；自动合并为单独明确选择，默认不启用。
- 允许的投机任务可以在隔离目录提前调查、复现或准备修改。无有用结果则静默结束，有价值时按授权产生可审阅交付。
- 本地准备、外部发信、PR 发布与合并分别检查权限。消耗预算或执行遇阻不构成扩大权限的理由。
- 来源正文、机器人评审和 CI 结果不自行取得新的明确授权；动作范围不能由模型从“值得做”推成“已经允许做”。

### D16. 外部 Watchdog

- 外部运维回路独立于被监督 Host，借鉴原型另一个 profile 的定时 Agent 检查与恢复。正常静默，故障分类后恢复或报告，人工 stop 保持。
- 任务语义监督使用独立 Session，对比目标、授权、报告、工具和交付变化，识别无效循环、偏离及无进展。
- 正常等待人、设备或外部条件有结构化事实，不能仅按时间认定失败。监督动作有频率与次数预算。
- 用户已确认：Watchdog 可自动查证和安全重试；任务语义纠偏或暂停前必须先问用户。提案包含观察证据、建议动作及影响，明确批准前不执行。未知外部结果和写权不明先对账，不能盲目重放。
- 用户已批准参考运维恢复：独立回路默认每小时检查，服务故障按流程尝试优雅重启，尊重人工 stop；来源/策略部件错误或缺 setup 不重启。优雅关闭按参考最多等五分钟，不强杀；同次巡检不循环重启。正常和恢复成功静默，相同未变化错误去重通知。
- 维护者可经受信入口以自然语言指令在线修改提示词或触发规则，按明确授权、revision 冲突检查与版本记录执行。未额外授予 Watchdog 自主修改规则、提示词或运行参数的权限；扩大权限与撤销人工 stop 不属于自动恢复。
- 运维巡检、Effects 队列退避和语义监督分开计量。参考退避延迟封顶不代表总次数有界；本项目既有重试次数/资源预算在对应切片验收，不由监督器自行扩大。
- 每次干预保存观察、依据、动作、结果及配置版本，监督器自身反复失败时明确请求人工处理。
- Watchdog 的自动接管必须先经过 Instance 锁、Host epoch/fencing 和设备 job 对账；它只能恢复原 Mandate 内可安全恢复的工作，不能解除人工 stop、暂停或权限撤销。无法证明旧执行已隔离时局部保持 unknown，其他工作继续。

### D17. 界面与权限继承

- 桌面初始采用统一对话与按需监督视图，优先展示问题、验收、受阻和失败。用户可追溯来源、决定、执行和回执。
- Worker 细节按需展开，正常状态不持续制造动画或通知。不同信道按其习惯组织内容，IM 简短，异步交付提供结构化证据。
- 用户可在后台执行中修正、停止和回答问题；高权限设置与设备授权由合适的用户入口完成。
- 上下文实例、来源准入、任务授权、工具权限、设备权限和外部发布权限分别检查。CLI wrapper 不被当作 OS 沙箱。
- 复用既有隐私和凭据能力时重新映射到 Instance、角色与 Environment，保护不会因去掉 Bot 调度模型而消失。

### D18. 迁移与工程交付

- 旧团队、群、记忆与 Session 先保留为只读历史，按明示映射导入角色和可共享资料。数据迁移使用新目录或副本，用户原有 DSH 数据保持只读。
- 切换时核查旧未完成工作，再决定是否建立新 Ticket；不将旧派活直接重放为新任务。
- 同一输入只由一套调度核心消费。旧核心退出与新核心启用有可核查切换点，导入失败不破坏原始资料。
- 移植兼容许可代码时保留版权和来源；产品文案与团队流程根据本项目撰写。前端生成、仓库分支和交付检查继续遵循项目规则。
- 本规格分多次完整切片交付，技术验证不通过则修订受影响决定与依赖；仅使用 DSH 公开扩展接口，必要上游能力缺口明确记录。

## Testing Decisions

### 测试接口与原则

用户已确认：Domain Engine 的公开命令与查询是主要测试接口。以事件和命令输入，经持久事实、可见状态、排队操作、报告与回执断言结果。测试不绑定私有 helper、内部类数量或实现调用顺序。

来源、存储、DSH Session、Channel 和设备执行在各自替换位置补合约测试；它们验证真实会变化的外部语义，不能用大量内部 mock 代替运行核心。领域测试使用可控时间与确定性适配器，来源与数据库适配器测试使用真实实现或可重复的协议替身。

### 分层证据与既有先例

1. 领域与适配合约：参考官方原型关于 Engine、follow-up、Policy、stage、delivery、Effects、Outbox、存储和并发的回归场景；按新接口复用行为期望，避免原样复制内部结构测试。
2. 隔离 DSH mock 集成：验证真实 Session、预设、输入、后台作业、取消、flush 和重启。使用独立临时数据与空闲端口，结束时停止本轮进程。
3. 故障演练：覆盖提交、派发、投递、入历史、报告、外发及设备响应窗口，分别验证单机和共享后端。
4. 真实模型与信道：小规模验证意图判断、范围遵守、跨信道指代、主动误触发与语义监督。确定性 mock 通过不能替代这层证据。
5. Windows 原生与正式部署：检查常驻、客户端关闭/重连、消息与问题界面、服务与设备恢复。界面变更保留真实截图或演示证据。

DS Bot 现有的请求身份、交接结果、上下文、隐私、记忆及桌面流程提供回归先例，迁移后仍验证相应用户保护。当前已有的 7 组内存实验只是有限领域证据，不视为完整集成或发布验收。

### 性能与完成标准

- 使用相同事件流比较单 Session、Router/Worker、加订阅直通后的结构。记录输入受理/响应延迟、完成时间 p50/p95、Router 调用与批次、token、直通比例、重复工作及通知。
- 故障与主动场景另记录恢复时间、未知结果、误触发、有效交付和监督干预次数。文章的合成实验数字不作为本项目承诺。
