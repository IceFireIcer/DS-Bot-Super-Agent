# T41：在运行、断连或交接中断时守住切换约束

- Issue：[T41 / #69](https://github.com/IceFireIcer/DS-SuperAgent/issues/69)。
- 实施基线：`03a2149`。
- 规格：v2.1 D06、D07、D09、D13、D14、D19；A20、A28、A29、A30；用户故事 28、85、88、91。

## 已交付

- Host 启动扫描 `handoff-state`，对 `requested | flushing | switching` 的未终结记录先对账再继续：每次启动最多恢复 25 条，扫描按 100 条/页、最多 10 页；超过预算的记录留待下一次启动，不无限扫描。单条恢复失败只把该记录写成 `handoff-recovery-failed`（下一步责任人 host），不会中止其余记录。
- 对账使用当前事实，而不是沿用崩溃前的判断：Ticket open、无 stop/constraint/waiting-human、无 ready report、setup 未失败、无未知外部结果；源 Assignment 的 ID、generation 与 running 状态仍与记录一致；没有活跃 Worker turn、`starting|running|cancelling|unknown` 的 job、子 Agent 或 preview。
- 环境身份重新核验：记录的源 Environment 必须仍以同一 kind/root 配置并授权原请求人；目标 Environment 必须仍配置、授权，并通过在线/目录/版本/指纹/权限/能力/容量选择；副本重新 `verify`。失败保持源 Assignment，并把原记录写成 `blocked`，不会回退到本机或其他设备。
- 恢复是“继续同一记录”而不是新建一次交接：保留原 `handoff.id`、源/目标身份、`recoveredAt` 和 `command` 回执；补写 `recovered` 步骤后重新 flush、重验目标/副本，再走同一个切换事务。恢复时也重新记录 settled job 证据（`jobs-reconciled`），不会因为走恢复路径而丢掉原 job 对账。恢复完成/阻断后，重放原 `commandId` 返回同一条记录。
- 原执行范围未隔离时不创建新代：任何活跃或 unknown 的 shell/PTY/job/子 Agent/preview 继续阻塞；切换事务在提交前再次检查 Assignment 代次、活跃 turn 和新增后台工作，失败记 `handoff-stale`。T41 不自动停止活跃进程，人工 stop/完成是前置条件。
- stop 优先：`stopTicket` 在设置停止约束、取消 scope Effects 的同一事务里，把未终结交接写成 `blocked`（`ticket-stopping` / 下一步责任人 human）。明确 resume 只创建新的源 Environment Assignment，不会继续旧的交接；要再切换必须重新走显式 `requestHandoff`。
- 暂停优先：`requestHandoff` 在 processing paused 时直接 `PROCESSING_PAUSED`；启动恢复和 resume 恢复扫描在暂停期间跳过，解除暂停后重新扫描，暂停窗口内不会提交切换。
- 未知优先：Ticket scope 内仍有 `unknown` **relay** Effect 时新增 `unknown-effect` blocker，不盲目切换；unknown 的 outbox 确认或 notice 不会阻塞执行环境交接（D07 只阻塞受影响操作）。目标/源不满足、离线、撤权、能力或同步证据不符继续是 `handoff-blocked`，不会被写成 completed。
- 每个 blocker 带 `nextOwner`（`operator | human | host`），`conversation(ticketId).environmentHandoff.blockers` 可显示具体原因和下一步责任人；例如目标不合格归 operator，人工 stop/未知结果归 human，活跃范围/Session flush 归 host。聊天预览新增 `Execution handoff` 面板，显示状态、源→目标、最后一步和每个 blocker 的 next owner。
- 旧代隔离沿用 Assignment ID + generation：恢复只操作与记录匹配的源代次；新代仍需通过带 `environmentHandoff` 记录的 relay 启动，旧 job/子 Agent/Input/回调不能唤醒新代。

## 验收证据

- 2026-11-10 Windows 11 / Node 25.4.0：`npm test -- --test-concurrency=2` **342/343**（唯一跳过是既有 Windows-only POSIX live-process 用例）；`npm run typecheck`、`npm run lint` 通过；T41 恢复测试 6/6。默认并发下本机已有负载敏感的 local command 用例超时（单独运行均通过），与 T41 逻辑无关。
- T40 已完成的 Windows Host → 临时 Ubuntu device 双向验收（2/2，11.6 s）仍是真实第二设备传输/Session 保持的证据；T41 的恢复验收使用隔离 SQLite 状态重放崩溃窗口，不伪装成新的真机断连实验。

## 边界

- T41 不自动停止活跃 shell/PTY/job/子 Agent；它们先阻塞交接，人工 stop 或完成并按原 job 对账后才允许切换。自动停止属于用户明确操作，不在后台恢复时擅自执行。
- 交接恢复预算为每次启动最多 25 条；更多未终结记录留待后续启动，不在一次启动里无限重试。
- T41 之前的交接记录没有保存 command 身份；这类遗留记录仍能被对账/阻断，但无法将原 commandId 与恢复结果对应起来。本票之后创建的记录都携带 command key/fingerprint，重放保持幂等。
- `requested/flushing/switching` 的恢复只处理同一 Host 的当前 Instance 与原始 source actor；跨 Host 接管和服务器替换仍按 T44，业务库/Session 共享后端按 T42/T43。
- 恢复不重放未知副作用，也不代替 T34/T35 的远端停止确认；目标或源离线时保持 blocked，不切回本机。
- 实际工作副本传输仍是 T39 manifest 之后的显式同步；T41 只恢复交接状态机，不新增自动传输或实时双写。
