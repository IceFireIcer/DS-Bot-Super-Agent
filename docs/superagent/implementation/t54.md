## 修复与固定事件流

旧结果无效于等事件流比较：订阅模式只投递一个初始请求和六个跟进，却将 events 标为 12；另两种模式处理 12 条，并且旧 Router/Worker 在 Assignment 存在时即计响应，订阅在 Input 入历史时计响应，没有等所有 Worker 完成。旧表及旧审查的“相同 12 条流”结论撤回。当前 JSON 是修复后的一次实际运行，不能与旧耗时直接比较。

三种模式共享同一份深层冻结的规范流：event-01–event-06 为六个初始请求，分别位于 thread-1–thread-6；event-07–event-12 是各原 Thread 的一次跟进。id、kind、threadId、text 在三种模式完全相同，Worker 收到被改写或未知正文会失败。seed 为 20261111，固定 Worker 延迟 20 ms，2 个正常槽 + 1 个人工优先槽，Router 候选上限 20。到达策略为严格规范顺序，每条在上一 Worker 回合完全结算后进入；本负载不测并发吞吐、突发公平性或批量聚合能力。

- singleSession：12 条流进入同一原生 Worker Session，没有 Engine/业务 Ticket/来源去重契约。
- routerWorker：六个初始来源事件按 Gate→Router assignment→Worker 执行；六个跟进先经一个公开 NativeSessions Router 回合，其唯一 forward_event 工具将原始事件原样交给同一个 Engine.receiveSource。**这是开发脚本明确加入的 Router 转发对照**，不是修改生产 Engine、关闭订阅或将跟进伪装成新 Thread；每个跟进仍进入原 Ticket/Worker Session。
- subscriptionDirect：六个初始事件走同一准入路径，六个跟进直接进入原 Thread 的订阅，不增加 Router 转发回合。每种 Engine 模式都只有六个 Ticket、六个 Worker Session，各处理两个事件。

每种模式独立建立临时目录、SQLite、Cordis Context、NativeSessions、Router Session、模型调用计数、通知观察及事件记录；完全清理后才运行下一种模式。没有共享 Router pending queue、历史、角色配置或计数。5 s Session 超时、每模式等待截止 25 s、Effects 十页和 Session 二十页分页限制；清理依次停止 Effects、关闭 Engine/Session/Context/Storage 并移除隔离目录，清理失败会报告而非吞掉。

## 测量边界与可核查事实

- startedAtMs：该规范事件进入模式入口；所有时间来自 performance.now，同一模式相对同一原点。
- acceptedAtMs：Engine 模式为 receiveSource 持久回执返回（含跟进 fan-out），**不是新 Ticket 接单时刻**；single 为 onMessagePersisted 观察到 user/message 的 flush，**不是业务接受回执**。受理边界在输出中分别说明，不比较为同一种业务 SLA。
- responseAtMs：模型适配器为该事件发出第一个文本 delta。适配器在相应输入准入/flush 确认后开始固定 20 ms mock 延迟；包括实际排队/创建/持久化时间，不是预填常数。
- completedAtMs：实际 Session 已 idle，公开持久日志含该原文 user/message、正确 assistant/message、reason=completed 的 turn/end，且没有活动 Worker handle、执行槽、等待槽或未结算 Effect。每条都保存输入、输出和结束序号；这是**回合完成，不是 Ticket ready/结果交付**。
- totalMs：所有 12 条 outcome 和全部执行范围结算后采集，包含同等日志核验成本；不含模式初始化、重放、状态重连与清理。每条 completion 延迟均有样本，p50/p95 使用 nearest-rank，样本数都是 12。

JSON 保存完整 canonical stream、流 SHA-256、每事件内容 SHA-256、Thread、Ticket/Session ID、路由、持久序号、文本产出与各边界时间。populationDigest 由实际 Worker 接收的事件顺序生成并与 canonical digest 比较。当前摘要为 8493a38fc5dcd54615b2067ffb86e44aaa1c5f5b1e900e4ec59fc83d5acf70b7。跨模式 Session ID 不交叉。

Router calls 是模型边界实际请求次数；Router turns 由实际 Router user-message identity 去重；Router batches 只计实际 record_batch_assessment 模型批次，不能把 Gate evaluation 或 assign_worker 回合冒称语义批次。本流是明确人类 direct 请求，Gate 直接放行，所以语义 batch 数为 0；intakeEvaluations 保留六次准入研判事实。Router/Worker 的 12 个 Router 回合含六次 assignment 和六次额外转发；订阅模式只有六次 assignment。每个回合工具步后的第二次模型请求同样计入 calls。

通知由注入的 mock DeliveryChannel 实际调用观察，保存 id、purpose、幂等键，并从公开 getTicketDeliveries 查询 sent ledger。两种 Engine 模式各有六次 acknowledgement，无 result；single 没有投递通道。通知重复按观察到的幂等键计算，不写死 0。计时后按原 command/object ID 重放全部 12 条来源事件，等 Effects 再次结算，通过前后真实 Worker、Ticket 和通知数量差计算重复项。single 的来源重放不适用，不声称它提供来源 exactly-once。unknown 通过公开 Effect/job 查询计数；happy-path 没有故障，不等于未知结果对账通过。
