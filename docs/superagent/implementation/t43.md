# T43：用共享后端持久恢复原生 Session

- Issue：[T43 / #71](https://github.com/IceFireIcer/DS-SuperAgent/issues/71)。
- 实施基线：`1de4b86`。
- 规格：v2.1 D09、D13；A10、A21、A31；用户故事 60、92。
- 前置：[T15 / #43](https://github.com/IceFireIcer/DS-SuperAgent/issues/43)（已关闭，SQLite Session 生命周期与 writer 契约）。

## 已交付

- `session-persistence.ts` 从 SQLite 专用实现改为公开 `Storage` 合约上的 `StorageSessionPersistence`。`session-meta`、`session-event`、`session-writer` 仍写入 `session-store` Instance 命名空间；SQLite 插件名、`databasePath` 配置和 `SqliteSessionPersistence` 导出保持不变，旧行为只是通过共享 provider 复用。
- 新增 `Storage.acquireWriterLease?(key)` 可选能力与 `WriterLease { active, backendPid?, release() }`。没有该能力的后端继续沿用 T15 的 owner PID 探测；有该能力的共享后端以租约为唯一 writer 权威，不再用本机 PID 判断另一台机器的持有者。
- 新增 `session-persistence-postgres` 插件（`ds-superagent/session-persistence-postgres`），接受与 `PostgresStorage` 相同的显式 `connectionString` 或 `host/port/user/password/database/ssl` 配置。它打开共享 PostgreSQL 后端并在同一进程内挂载公开 `SessionPersistence` 服务。
- PostgreSQL writer 租约是专用池连接上的 session-level advisory lock：`pg_try_advisory_lock(hashtextextended('ds-superagent-session-writer:<sessionId>', 0))`，释放时显式 `pg_advisory_unlock`。同一 Session 的第二个进程或同进程第二个 provider 得到 `SessionAlreadyOwnedError`；重复或正在创建的同一身份得到 `SessionAlreadyExistsError`。持有进程崩溃时 PostgreSQL 关闭其连接并释放锁，后继可以接管。
- 写租约只约束写 handle；`open(id, 'read')` 不需要租约，因此另一合法进程可以在 writer 活动时读取同一段完整历史。租约连接断开时 `lease.active` 变为 false，旧 handle 的 `append`/`flush` 在写事务前抛 `SessionOwnershipLostError`。
- durable writer 行仍带单调 `epoch` 与 `leaseBackendPid`。每次 `append`、`flush`、`close` 都在同一 `session-store` 事务里重读 writer 行并比对 epoch，且在事务内再次检查租约仍然 active，所以租约丢失后被新 owner 推进 epoch 的旧 handle 仍然不能写；已断开租约的 handle 连 `close` 也抛 `SessionOwnershipLostError`，不会把已失去的写权伪报成成功关闭。
- `append` 每次调用持久提交，构造期后缀在 `session/created` 广播前已经可读；`flush`/`close` 的持久失败保持 handle 与写权，`create` 后从未物化的 Session 仍在 close 时删除自身记录。服务替换或重开读取完整历史，旧 handle 只报已关闭，不会重新取得写权。
- COMMIT 应答丢失时无法判断持久结果；`append`/`flush` 收到 `COMMIT_UNKNOWN` 会保守地把 handle 视为已物化，避免 `close` 删除可能已提交的 header 而留下孤儿事件日志。若实际回滚，Session 保留为可查询的空日志；若实际提交，完整历史可恢复。
- 修复 `PostgresStorage.transaction` 的错误分类：此前回调抛出的任何非 `CoreError` 都会被翻译成 `STORAGE_ERROR`，从而抹掉 `SessionOwnershipLostError`、`SessionAlreadyExistsError` 等 DSH 领域错误。现在 `CoreError` 原样透传，带 SQLSTATE 的服务器错误仍按既有映射翻译，连接失败仍归 `COMMIT_UNKNOWN`，其他领域/验证错误原样抛出。
- `PostgresStorage.close()` 会释放仍被 handle 持有的租约，再结束租约池与主池；释放幂等，且连接断开后保留错误监听直到 release（被终止的 backend 可能发出多个连接错误）。这样最终事务失败的 handle 不会让关闭无限等待，同时正常 close 的顺序仍是先确认 writer 行再释放租约。
- `superagent/scripts/build.mjs` 增加 `session-persistence-postgres` 构建入口，`package.json` 暴露对应 export。T42 的 PostgreSQL 测试启动代码提取为 `test/fixtures/postgres-harness.mjs`，供两个 PostgreSQL 测试文件复用，不改变业务后端行为。

## 验收证据

### 真实 PostgreSQL 契约

`test/session-persistence-postgres.test.mjs` 在真实 embedded PostgreSQL 17.11（Windows x64，只监听 `127.0.0.1` 随机端口，`fsync=on`、`synchronous_commit=on`，每次运行随机密码，每个用例独立数据库）上运行 **12/12**：

1. 公开 handle 合约：create/重复 create/第二 writer/只读 handle、三段连续 append、`stat`/`list`、flush/close 后重开续写。
2. seeded fork 保留 `parentSession`、`isSeeded` 与 `inheritedEventCount`。
3. 两个真实操作系统进程争用同一 writer：第二个进程得到 `SessionAlreadyOwnedError`，重复 create 得到 `SessionAlreadyExistsError`；原 owner 优雅关闭后子进程接管并续写；父进程在子进程持有期间只读历史；子进程无 close 直接退出后，父进程在锁释放后接管并读到崩溃前事件。
4. 真实 `pg_terminate_backend` 终止租约连接后旧 handle 的 append 与 close 均抛 `SessionOwnershipLostError` 且日志不变；数据库 writer 行 epoch 被推进后 append/flush/close 全部被拒绝。
5. 真实 PostgreSQL 触发器在 `session-meta` 更新时抛服务器异常：flush 与 close 都失败但 handle 仍持有写权，移除触发器后可继续 append 并成功关闭。
6. `after-commit` 代理抑制一次真实 COMMIT 应答：append 报 `COMMIT_UNKNOWN`，随后 close 不删除 header，换直连后端仍能读到已提交的事件与 header。
7. 同一共享后端的业务事务回滚后，`session-store` 日志不受影响并可正常创建与读取。
8. 注入 flush/close 事务失败后仍持有写权、可以继续 append 并最终成功关闭；另一 provider 在失败期间仍得到 `SessionAlreadyOwnedError`。
9. 替换 provider 后读到完整历史并续写；旧 handle 只报 `SessionHandleClosedError`，不会重新取得写权。
10. 公开 DSH loop：真实 `ctx.sessions.fork` 的种子 Session 在 `session/created` 广播时，构造记录已经能从 PostgreSQL 读回，数量、seq 与 seed 一致。
11. 公开 DSH loop：构造后缀持久失败时不广播 `session/created`，不留下可被 `stat`/`list` 误认的 Session。
12. 公开 DSH loop：Worker 第一回合后销毁整个 native Context，第二个 Context/适配器从同一 PostgreSQL 恢复同一 Session，第二回合提示词包含第一回合原文与第二回合输入，旧事件前缀逐条不变。

## 边界

- 每个活动写 handle 占用一条租约连接；租约池与主池各自使用 `maxConnections`，部署必须按并发 writer 数预留连接。本票不提供跨池共享配额，也不把 T42 的单命令基准当作 Session 并发预算；资源比较留给 T54。
- TCP 未关闭的网络分区可能让 PostgreSQL 暂时仍认为旧租约有效，接管要等到连接被检测为死亡；这期间不会双写（epoch 仍校验），但可能等待。复制、failover、TLS、连接池调优与掉电持久性均未验证。
- 一个 PostgreSQL 内可以同时承载业务记录与 Session 记录，二者以不同 Instance 命名空间和事务分离；恢复业务库不恢复 Session，也不回滚外部副作用。Session schema 仍随共享后端版本 1 一起初始化。
- 本票只验证同一 PostgreSQL 上的合法进程共享历史与恢复，不实现 T44 的服务器 Host 替换、T45 的认证客户端接入或跨 Host 双向交接。真实模型、外部信道与第二设备不在本票。
