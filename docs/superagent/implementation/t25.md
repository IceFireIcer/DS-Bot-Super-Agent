# T25：从 GitHub 来源可靠接收 Issue、PR 与评审事件

- Issue：[T25 / #53](https://github.com/IceFireIcer/DS-Bot-Super-Agent/issues/53)。
- 固定实施基线：`a13db2e`。

## 已交付

- `SourceKind` 扩展为 desktop/github/feishu/schedule，Thread 作用域支持 `allowedThreadPrefixes`，不把动态 GitHub/飞书 Thread 硬编码成固定清单。
- `GitHubSource` 校验 host 配置的 owner/repo、原生编号与来源身份；把 issue、pull request、review、CI、comment 映射为稳定 Thread/object 身份，保存 opaque/sequence 原生版本与删除证据。
- 来源自身消息过滤但推进游标；其他事件只在 `receiveSource` 记录成功后推进持久 `channel-cursor`。乱序页按游标排序，重放不重复接单。
- 同编号、同用户 ID 的两个 GitHub 实例不共享对象或作用域；越界仓库拒绝。
- `GitHubPoller` 在 setup 成功后轮询；单次来源失败进入 `failed` 健康并保留游标，退避后重试；`stop()` abort 并等待当前轮询结束，不吞掉已记录事件。
- `poll` 对越界/畸形项计数并跳过（推进游标），对记录失败停止本页并保留游标；Poller 健康暴露 `malformed` 与 `failedItems`。
- `GitHubCliTransport` 走已认证的 `gh api`，不保存或打印任何令牌：映射 issue、pull request、review 与 CI check run；PR 的 404 变为带删除依据的 `deleted` 事件，其他 API 故障仍是来源失败，二者不会混同。
- 适配器已给出的规范序号 cursor 直接作为原生版本；真实 API 的复合 cursor 才按 `updated_at` 与资源 id 派生规范序号，避免把同一秒的两个事件压成同一版本。
- 传输按 100/页、最多 10 页读取 issue 列表，并按持久游标过滤；单轮网络请求有声明期限，超时记为 `SOURCE_TIMEOUT` 且保留游标。
- issue 快照按 `state_reason` 区分 reopened、按 `updated_at` 与 `created_at` 区分 edited；已删除的 issue 不再出现在列表里，因此删除证据只对 PR 的 404 可得。

## 边界

- 模型为 mock，不证明模型研判质量。
- 议题、PR、评审与 CI 由验收脚本经 `gh` 创建，不是外部用户的自发流量。
- 已删除的 issue 与 review 编辑没有可核查的真实轨迹；这两项仍只有协议映射，没有真实信道证据。
- T25 仍 open，等待合入 `dev` 与发布。
