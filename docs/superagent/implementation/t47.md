## 已交付

### 1. 独立 Watchdog 进程与公开入口

- 新增公开 `Watchdog`（`ds-superagent/watchdog`）：默认每小时巡检，第一次巡检立即执行；`inspectOnce()` 供调度器或运维手工调用。
- 新增 `ds-superagent-watchdog` CLI（`dist/watchdog-cli.js`）：独立进程，参数为 `--database` 或 `--postgres`、`--instance`、`--status`、`--host-command`/`--host-arg`、`--interval-ms`、`--grace-ms`、`--max-restarts`、`--restart-window-ms`、`--version`；默认循环，`--once` 做一次诊断巡检。
- 新增 `ProcessWatchdogHost`（`ds-superagent/watchdog-process`）：Host 子进程写原子状态文件（PID、时间、epoch、来源、setup、组件、正常等待、接管/暂停、未知副作用），并监听一个 IPC `shutdown` 消息。状态过期或 PID 不存在即服务故障。
- 没有给 Watchdog 自动修改角色、提示词、策略或权限的入口；语义纠偏属于 T48。

### 2. 分类，而不是“进程不在就重启”

| 观察 | 动作 |
| --- | --- |
| 服务健康 | 记录，静默。 |
| 暂停、接管对账中、有等待人/设备/外部条件的 Ticket | `normal-wait`，不重启。正常等待不是故障。 |
| 来源失败、策略/交付/outbox 组件失败、未知外部副作用 | `component-failure`，不重启；按未变化错误去重通知。未知副作用不重放。 |
| setup 缺失或失败 | `setup-missing` / `setup-failed`，不重启；通知配置人。 |
| 服务不可达或 Host 进程消失 | `service-failure`，才进入优雅重启。 |

分类顺序先看组件与 setup，再看服务：即使服务探测也失败，只要同一份观察里仍有 setup/来源/策略问题，就不重启 Host，避免把账号或目录问题当成进程故障。

### 3. 优雅重启，最多五分钟，不强杀，不循环

- `graceMs` 默认和上限都是 300,000 ms（五分钟）；`stop()` 另加 1 秒硬上限，适配器即使忽略 abort 也会被记为 `restart-timeout`。
- 停止使用 Host 自己的 IPC `shutdown`，不发送 SIGKILL；`ProcessWatchdogHost` 对“不是本适配器启动的、仍在运行的 Host”明确返回 `timeout`，不会误报 `stopped` 后启动第二个 Router。
- 每次巡检最多一次 stop/start；不会在同一巡检里循环重启。
- `start()` 的契约是：先取得 Host 租约、完成替换对账，再返回。T47 的 Windows 演练用真实 `Engine.acquireHost()` + 原生 Session 运行时，替换后 `takeover.state: completed`、`outcome: resumed`；T44 的合法租约/fencing/设备对账由同一入口执行。
- 重启后重新探测；健康则记 `recovered` 且静默。停止超时、启动失败、重启后仍不健康或预算耗尽，记录 `escalate: true` 的通知，明确请人处理。

### 4. 观察、依据、动作、结果、版本和预算都是持久事实

- 每次巡检写入 `watchdog-state`：`observation`（当次完整探测）、可选的 `after`（重启后探测）、`kind`、`action`、`result`、`fingerprint`、`version`、`budget` 与最近 100 条历史。
- 重启预算默认 3 次/6 小时；每次尝试（包括停止超时）消耗预算；预算耗尽后不再重启，只发一次 `budget-exhausted` 通知。
- 通知按未变化错误 fingerprint 去重；健康、正常等待或恢复成功会清除 dedupe key，之后同类错误再次出现仍会通知。通知发送失败记 `result: failed` 且不写 dedupe key，下次继续尝试，不伪报已送达。

### 5. 不解除停止、暂停和撤权

- Watchdog 没有 `resumeTicket`、取消暂停、恢复撤权或重放 Effect 的入口；它只停止/启动 Host。
- 停止、暂停、人工等待、接管对账中、未知 Effect/job 都只作为观察事实；重启后的工作承接由 T44 的 takeover 按原 stop/等待/撤权约束处理。

## 使用方式

```sh
cd superagent
npm run build

# 一次诊断；Host 由 CLI 启动，结束后会优雅停止
node dist/watchdog-cli.js \
  --database "$PWD/.t47/state.sqlite" \
  --instance private \
  --status "$PWD/.t47/host-status.json" \
  --host-command node \
  --host-arg "$PWD/dev/t47-host.mjs" \
  --host-arg --database --host-arg "$PWD/.t47/state.sqlite" \
  --host-arg --instance --host-arg private \
  --host-arg --status --host-arg "$PWD/.t47/host-status.json" \
  --once

# 独立常驻
node dist/watchdog-cli.js ... --interval-ms 3600000
```

`dev/t47-acceptance.mjs` 结束后停止本轮 Host、关闭 SQLite/PostgreSQL 并删除临时目录；不读取用户自己的 DSH 数据。

## 边界

- **“托管配方”是共享后端配方，不是远程托管部署。** 本轮 PostgreSQL 运行在同一台 Windows 机器上的 embedded PostgreSQL 17.11；远程服务器、真实托管数据库、网络分区和跨机 Watchdog 没有本次运行证据。
- **设备对账的具体设备路径仍属 T44。** T47 的真实演练让新 Host 走 `Engine.acquireHost()` 的 Execution takeover，seeded Assignment 得到 `resumed`；真实第二设备/远端 job 的对账证据在 T44 的 Windows→Ubuntu 两进程验收中。T47 没有重新伪造一个远端设备。
- **没有控制真实 OS 睡眠或关机。** 本票是服务故障恢复；T46 的宿主生命周期边界仍适用。
- **没有安装 Windows Service / 计划任务。** CLI 是独立进程入口，部署形态、服务注册、日志轮转和开机自启仍属于部署/产品集成（T55）。
- **Watchdog 是单实例假设。** 同一 Instance 同时启动两个 Watchdog 没有额外的协调锁；运维部署应只启用一个。当前记录是 `watchdog-state` 单记录，后写覆盖前写。
- **通知只调用调用方的 `notify`。** CLI 输出到 stderr；没有飞书/GitHub/桌面推送通道，也未做跨小时的外部通知重试。
- **没有语义监督。** 判断无效循环、偏离目标或提出纠偏/暂停建议属于 T48；T47 不判断工作质量，也不修改角色/提示词/策略。
- 没有发布；没有等待 CI 结论。
