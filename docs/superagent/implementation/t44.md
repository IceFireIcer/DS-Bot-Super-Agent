## 已交付

- `HostLease.acquireWithPrevious()` 把“把 epoch 推进到新 Host”和“写入 pending takeover 记录”放在同一个业务事务：检查未过期租约、拒绝并发有效写者、为被替换的 Host 记录 `previousHostId/previousEpoch/previousToken`，然后返回 `HostAcquisition { lease, previous? }`。租约带 `owner`（进程身份）：同一进程里的多个 `Engine` 续租同一 epoch，不创建接管记录；另一进程即使复用相同稳定 `hostId`，在租约未过期时也得到 `HOST_LEASED`。已释放的租约代表前一个进程干净停止，只推进 epoch、不重跑对账；只有“过期但未释放”的租约按被替换 Host 对账。
- 新 epoch 在完成对账前不能接新工作。`host-takeover` 记录是持久事实，状态从 `pending` 走到 `completed`；`Engine.getHostTakeover()` 返回当前 epoch 的完整决策，包含每个 Ticket 的 `outcome`、前后 Assignment、Session 和 blocker 证据。
- 准入检查放在真正创建工作的那个事务里：`submit`、`acceptSource`、`accept`、`answerAttention`、`resumeTicket`、`retryTicket` 在完成命令/事件重放检查后、创建新 Assignment 或输入前读取 pending 记录。这样 COMMIT 应答丢失时仍然按原 commandId/eventId 对账并返回原回执，不会因为一次独立探针事务把原命令变成“未知”。
- `Execution.takeOverHost()` 对旧 runtime 留下的每个 Ticket 先按稳定 ID 对账：注销中的离线 stop 先 `inspectRange` 原设备范围；远端 job 先按 device incarnation + job ID 查询、接管 live range 或标记 unknown，再决定 Assignment。数据库业务锁不被当成设备进程静止的证明。
- 对账后才结束旧 Assignment 并按情况处理：
  - `resumed`：保留 Ticket、Session、Environment，创建带 `recovery = { reason: 'HOST_REPLACED', previousAssignmentId, takeoverId }` 的新 Assignment，恢复提示要求先核查目录、版本控制、外部状态，并按原 ID/job ID/marker 对账每个外部动作。
  - `waiting-job`：可观察的 live 设备作业改绑到新 Assignment，保留原 job ID 和输出；作业完成仍唤醒新代。
  - `input-pending`：已持久但尚未承接的人工跟进留在原 Ticket，旧 Assignment 结束后由输入恢复投递一次，不重复追加用户消息。
  - `stopped`、`waiting-human`、`handoff-pending`：保留原约束，不创建 successor；stop 的 `recoveryReason` 记为 `HOST_REPLACED`，未确认的取消仍不可恢复。
  - `revoked`、`blocked`：结束旧 Assignment；撤权优先于等待人工，会 supersede 旧 Attention、清除 waiting-human 约束并把 intent 标为 `recovery-blocked`，只记录 blocker，不自动恢复。未知 job/效果/子代理、待清理预览等无法证明静止的项形成一个结构化 Attention，选项为“已人工对账，继续”与“保留 unknown，继续”，停止走原有 stop 命令；未回答前不启动新 Assignment。
  - `idle`、`ended`：结束旧代，不制造空 turn。
- 旧 Host 的隔离由既有 Host 守卫承担：每个业务事务核验当前租约的 hostId/token；被替换后旧进程的读写、reconcile 与新提交都得到 `HOST_LEASED`，SIGKILL 后复活也一样。旧 Session writer、旧 Assignment 回调和迟到 job 结果不能改写当前事实。
- 同一 Host 在接管中途崩溃后重启，`acquireHost()` 会重读同一个 pending 记录并完成对账，而不是另造一份；重复获取返回同一 epoch 和同一 successor。
- `Jobs.reassign()` 只移动本 runtime 仍持有、未终结的作业记录，并更新 job 索引；旧 runtime 的作业不会被伪装成本 Host 已接管。
- 生产入口 `apply()` 在启动 Host 时显式 `acquireHost()`；清理时先停 Effects 再释放租约，避免释放事务与后台扫描竞争而丢失。此前仓库里没有任何调用 `acquireHost()` 的入口，崩溃后的新进程会一直停在 `HOST_LEASE_EXPIRED`。
- 没有 native runtime 的接管不再静默“完成”：旧代结束、intent 标为 `recovery-blocked`，每个 Ticket 记 `blocked`/`takeover-failed`。

## 验收证据

### 真实两进程共享 PostgreSQL

`test/host-takeover-process.test.mjs` 使用真实 embedded PostgreSQL 17.11（随机端口、随机密码、独立数据库）和两个真实操作系统进程（`test/fixtures/host-takeover.mjs`）：

1. 进程 A 取得 epoch 1 并持有 Ticket/Assignment/Session；共享 Session 写入被 A 的 writer 租约占住。
2. 进程 B 在租约未过期时得到 `HOST_LEASED`，不能并发成为有效写者；另一个复用 A 稳定 `hostId` 的进程同样得到 `HOST_LEASED`，不会靠同名身份“续租”。
3. 父进程尝试写同一 Session 得到 `SessionAlreadyOwnedError`，但可以只读完整历史。
4. SIGKILL A、等待租约过期后，B 取得 epoch 2；takeover 为 `completed`，Ticket 结果为 `resumed`，旧 Assignment 结束，新 Assignment 为 `pending` 且带 `HOST_REPLACED`，历史 2 条。
5. B 在共享后端上写入并读取同一 Session，`eventCount` 从 1 增到 2，证明替换后 Session 写权随新 Host 转移。
6. 复活旧进程 A 后再次读取同一 Ticket 得到 `HOST_LEASED`，旧进程不能回写。

### 领域与恢复行为

`test/host-takeover.test.mjs` **10/10**：

1. 合法接管结束旧 Assignment、保留 Session/Environment、新代带恢复说明；旧 Host 的读写/提交/reconcile 和复活进程均被 `HOST_LEASED` 拒绝；Worker 收到 Host 替换提示。
2. 未确认的 stop 跨替换保留为 `stopped`/`HOST_REPLACED`，没有 successor，恢复仍报 `CANCELLATION_UNCONFIRMED`。
3. waiting-human 问题跨替换保留；回答后创建新代并清除约束。
4. 未知 job + 未知 effect 生成一个带证据的 Attention，旧代结束且没有 successor；回答“保留 unknown”后才创建新代。
5. live 远端作业按原 ID 接管并改绑 successor，完成后唤醒新代；successor 带 `HOST_REPLACED`。
6. 已持久但未投递的人工跟进在接管后只进入 Session 一次，旧 Session 身份保留。
7. pending 记录阻止新工作，原命令重放仍返回原回执；同一 Host 再次获取会完成同一记录，且不重复 successor。
8. 同进程内重启沿用已释放租约的下一 epoch，不产生新的 takeover；另一个进程在同一稳定 ID 上仍被未过期租约挡住。
9. 撤权优先于等待人工：旧 Attention 被 supersede、约束清除，没有可恢复的 successor。
10. 没有 native runtime 的接管会结束旧代并以 `takeover-failed` 阻断，而不是报告成功。

## 边界

- 不承诺半个模型 turn、Shell、PTY 或设备命令从原执行点续跑；恢复只依赖持久事实、原 ID 和现实对账。Worker 的恢复提示是行为约束，不是对旧进程已停止的证明。
- 设备侧的 live-range 接管在领域测试中由公开设备契约替身验证；真实第二设备的 daemon 重启、原 job ID 查询与取消证据来自 T35/T37，本票没有改变设备协议。
- 接管按当前 epoch 记录；如果完成对账的新 Host 在下一轮又被替换，新 epoch 会重新扫描所有旧 runtime 的 Assignment，而不是继续旧 epoch 的记录。每次扫描最多 1000 个有效 Assignment，超出以 `HOST_TAKEOVER_BUDGET` 失败并保留 pending，避免无界恢复。
- 真实托管部署、复制/failover、TCP 半开网络分区和掉电时序未验证；embedded PostgreSQL 是两个真实进程共享的真实隔离数据库，不是生产 SLA 证据。
- 本票未实现 T45 的认证客户端接入、跨 Host 双向交接或资产/附件迁移；这些仍由后续票承担。
