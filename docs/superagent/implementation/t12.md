# T12：长命令异步执行并把完成事件送回原 Worker

- Issue：[T12 / #40](https://github.com/IceFireIcer/DS-Bot-Super-Agent/issues/40)。依据：规格 v2.1 D08/D09/D14，A07/A08/A09/A33，用户故事 7、67。
- 固定实施基线：`bea20f1`；实现提交：本票提交。
- 公开测试边界：`Engine.submit`、`receiveSource`、`acceptSource`、`conversation`、`listJobs`、`getJob`、`cancelJob`、`stopTicket`、`listSlots`、Effects 派发/回执，`Jobs`/`LocalEnvironment` 契约，以及真实 Effects、真实本地子进程与原生 DSH Router/Worker Session 的 mock 模型集成。未使用真实模型、外部账号或用户 DSH 数据。

## 行为

后台执行通过新的 `start_command` 原生工具启动：它立即返回可追踪的 job 身份（`jobId`、命令名、`running`、`startedAt`），不等待进程结束，因此当前推理步结束就能处理新输入。`job_status` 按需读取状态、确认退出与有界输出，`cancel_job` 由 Worker 自行取消。读取的是 Provider 的有界保留窗口（每流 8192 字节），重复查询不消费输出；输出经既有脱敏后进入事实，lossy 流整段丢弃而不泄露被截断的密钥尾部。job 身份包含所属 Ticket/Assignment/generation 与 Environment，同 ID 跨参数不会串线。

每回合结束后，若该 Assignment 仍有 `running` 的 job，回合不报 idle：Ticket 保持 `worker-background`，执行槽继续被占用，因此后台工作纳入 T11 的槽预算，普通启动仍按 `maxSlots` 排队。job 完成、取消或到达声明等待上限时，完成事件以 relay 送回原 Worker 的同一 Session；此时该 Ticket 通常仍持有自己的槽，唤醒直接复用它，若已不持有时按 `activation: 'background'` 走普通槽，绝不占用人工的额外槽。事件正文携带状态、退出码与输出，本身不构成 ready。迟到完成只有在 Ticket 仍 open、无 constraint、且 Assignment 的 id 与 generation 都仍是当前代次时才唤醒；人工 stop、暂停、等待人工、ready 交付或换代之后都不会唤醒任务或新一代。

清理按归属进行：`stopTicket` 在同一事务里持久取消该 Ticket 的活动 jobs 并终止进程范围；`cancelJob` 先提交持久取消再杀进程，被拒绝的命令不会误杀工作；Assignment 交回人工（`waiting-human`）或以 ready 结束时，其 jobs 以 `assignment-ended` 取消。取消分两段：先写 `cancelling`，只有在观察到 managed range 为空后才写 `cancelled`（并在丢弃 handle 前读取有界输出尾部）；本 Host 无法观察到的范围记为 `unknown`，不会被当作已停止。声明等待上限默认 30 分钟（`jobs.waitMs`，100 ms–1 h），到限终止进程范围并记为 `cancelled`/`deadline`，不会当作交付成功。每 Ticket 默认最多 4 个并发 job（`jobs.maxPerTicket`），该检查在启动事务内执行，因此两个并发启动不会同时通过；重复超出预算的启动会先被拒绝，其进程随即终止，不留下记录或 handle。进程异常（无法确认退出）记为 `unknown`，`settled:false`、`succeeded:false`；旧 runtime 遗留的 running 记录、以及本进程已不再持有 handle 的 running 记录都读作 `unknown`，因此中断的结算不会永久占槽。

活动 job 另有一份 `job-active` 索引（只存 id 与 assignmentId），准入、占槽判断和取消清扫都读索引而不是有界的历史扫描，因此历史很长也不会隐藏仍在运行的工作。索引是派生读模型：它由写入路径维护，读取时清理失效条目；直接写入 job 记录（例如恢复演练）不会自动补建索引，需在下一次读取时才回到索引中。

job 记录是证据，不做自动删除（审计明确禁止擅自增加自动清理）。单票查询有界为最新 100 条，因此长寿命 Ticket 仍可查询，旧记录留在存储中。

槽持有的收尾是幂等的：只有当本进程没有活动回合且该 Ticket 已无 running job、也没有排队中的 relay 时，`worker-background` 才回到 `worker-idle` 并释放槽；`conversation`/`listJobs` 每次读取都会做这项核对，因此人工取消最后一个 job 后槽会立即释放，而不会等到下一次扫描。

## 验证

```sh
cd superagent
npm run typecheck
npm test
npm run lint
npm run build
node dev/jobs.mjs
```

2026-11-08，Windows x64 / Node 25.4.0：新核心全量 **142/142** 通过（T12 新增 12 项，其中 1 项在 `Slots` 契约上验证 job 完成不占人工额外槽），typecheck 与 lint 无错误。T12 定向覆盖：长命令立即返回启动事实且回合在进程仍运行时结束、独立请求在长命令期间被受理并完成、完成事件带退出码与输出回到原 Worker 且本身不构成 ready、人工改方向时 Worker 取消正在运行的 job、人工 `cancelJob` 的授权/重放/冲突及其确认后的输出、stop 终止后台工作且迟到退出不唤醒、后台工作占槽使新启动排队、旧代次完成被跳过、每 Ticket 并发上限（超额启动不留下 record 或 handle）、声明等待到限、重启与本进程已不再持有的 running 记录都读作 unknown、历史超过查询预算时仍返回最新并保留证据、活动 job 不被历史扫描淹没。

`node dev/jobs.mjs` 在声明负载（12 秒真实 Windows 子进程、60 秒后台等待、50 ms 扫描）下实测：长命令回合在命令仍运行时约 173 ms 返回；独立请求在长命令期间约 333 ms 得到结果，此时 job 仍为 `running`；方向修正与取消约 24 ms 完成（含确认进程范围静止的等待）、随后槽持有为 0；正常结束的完成事件约 375 ms 内送回原 Worker，退出码 0，且未被当作结果。

## 边界

本票验证异步启动、完成事件回送、槽预算与按归属清理，不实现子代理（T13）或交付验收时的预览服务与槽释放（T14），也不代替 T54 的性能比较。真实模型、外部信道、第二设备与正式部署验收仍待对应票；上述数字来自确定性 mock 负载与真实本地子进程，不是生产吞吐或 SLA。并发 job 上限、等待上限与输出窗口是本票声明的预算，超出即拒绝或终止，不做无限重试。

两处需要随票说明的跨票改动：版本化来源现在可以在 `acceptSource` 上显式绑定一个已授权的本地 Environment（与 `submit` 一致），这是本票为让真实长命令可达而扩展的最小入口，不改变既有来源范围、事件当前性或 Mandate 授权；`stopTicket` 判定"是否仍有本地执行"时把活动后台 job 计入，因此一个"回合已结束但 job 仍在跑"的 Ticket 会显示 `stopping` 直到范围确认静止，这是 T09 停止语义在后台工作下的必要延伸。job 记录不做自动清理（审计明确要求保留原始证据），容量与保留策略留给后续容量票。
