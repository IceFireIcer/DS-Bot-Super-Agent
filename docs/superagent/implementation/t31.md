# T31：在飞书就地回答问题并可靠交付

- Issue：[T31 / #59](https://github.com/IceFireIcer/DS-SuperAgent/issues/59)。
- 固定实施基线：`cd1575a`（T30 的飞书 OpenAPI 传输已合入当前分支）。

## 已交付

- `FeishuOpenApi.replyMessage` 按官方 `POST /open-apis/im/v1/messages/:message_id/reply` 以文本回复原消息，正文不超过 Feishu 的 150 KB 文本限制。
- IM 回复默认截断到 4000 字符并标注完整内容在 Ticket 中；可按通道配置调整，但不超过平台限制。
- `FeishuDeliveryChannel` 把确认、问题、回答和结果都回复到交付目标原消息：目标事件必须是 `message:<native message id>`，否则永久拒绝。
- 幂等：对 Outbox 的稳定 `idempotencyKey` 取 SHA-256 前 32 个十六进制字符（128 位）作为 Feishu `uuid`（≤50 字符）；重试与 reconcile 复用同一 uuid，Feishu 在 1 小时内至多成功回复一次。
- 回执映射：HTTP 429/5xx、频率限制与 token 失效为 `transient`；消息已删除（230110）为 `DESTINATION_GONE`；已知权限/参数错误为永久失败；未知 Feishu 码保留为 `unknown` 而不是静默丢弃；中止保持可重试，不宣称数据库提供平台 exactly-once。
- transient 重试耗尽时 Outbox 回执保持 `pending`（带原因），不会被标成 `dropped`；来源恢复后仍可按原 uuid 重试。
- 问答链路：飞书的人类问题形成 Attention；授权回答通过 `sourceEventId` 绑定当前人类消息并恢复原工作；结果继续回复原讨论。确认、问题、回答和结果仍回各自对应消息，不广播私人上下文。
- 人类在同一 Thread 的后续回复在接收事务内自动回答唯一匹配的 waiting Attention 并恢复原工作；同一 Thread 有多个 waiting 问题时保持待查，不猜测。
- 临时不可达按 Outbox 等待/重试；永久不可达记录 dropped，不改投其他对象；重复 Attention 由既有状态去重。

## 验收证据

- 协议夹具：`reply` 端点的 POST 路径、文本 content、`msg_type` 与 uuid、uuid 复用、transient/永久/已删除/未知码/不支持目标/超大正文映射、IM 截断。
- 端到端夹具：飞书问题 → Attention → 授权回答 → Worker 继续 → 结果；确认、问题、结果都以 `om_q` 为目标回复，结果回执为 `sent`，Ticket 正常结束。
- 没有使用真实飞书租户；真实隔离群验收仍未完成。

## 边界

- 维护者明确暂缓真实飞书群测试；当前没有使用任何飞书应用凭据。
- Feishu 的 uuid 去重窗口是 1 小时；Outbox 的重试在此窗口内，响应丢失超过窗口时仍需外部查询对账。
- `reconcile` 仍以同一 uuid 重发，不是平台查询；超过去重窗口的迟到对账可能重复，记录中不宣称平台 exactly-once。
- transient 耗尽后保持 pending 但效果已停止自动重试，需要来源恢复后的显式重试/对账入口。
- 同一 Thread 有多个 waiting 问题时自动回答不会猜测，仍走显式回答入口。
- 不设置 `reply_in_thread`；按官方说明，若原消息本身是话题消息，回复会默认以话题形式发送。话题容器的历史读取仍属 T30 的后续范围。
- 没有 host/CLI/UI 入口；交付由公开 Engine 与注入的 `FeishuDeliveryChannel` 完成。
- T31 仍 open，等待合入 `dev`、真实信道验收与发布。
