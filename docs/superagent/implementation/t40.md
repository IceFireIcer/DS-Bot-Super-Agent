# T40：在安全边界双向交接执行环境

- Issue：[T40 / #68](https://github.com/IceFireIcer/DS-SuperAgent/issues/68)。
- 实施基线：`7eeabd7`。
- 规格：v2.1 D07、D09、D13、D14、D19；A27、A28、A29；用户故事 85、86、87。

## 已交付

- 新增独立模块 `src/environment-handoff.ts`，集中交接记录、阻塞项、状态判断、提示文本和 `handoff-state`/`handoff-history` 持久化，避免 `Execution` 因交接承担多个不相关改动原因。
- 新增 `EnvironmentHandoffView`，状态为 `requested | blocked | flushing | switching | completed`，记录源/目标 `EnvironmentLocation`、源 Assignment ID 与 generation、目标 Assignment ID 与 generation、工作副本 ID、请求人/理由/时间、已对账的 settled job、完成时间，以及带时间的 `steps`。`Engine.getEnvironmentHandoff(ticketId)` 和 `conversation(ticketId).environmentHandoff` 可查询同一条事实。
- `Engine.requestHandoff({ commandId, ticketId, targetEnvironmentId, reason })` 只接受这四个字段，校验稳定 ID、1–2048 字节理由、Instance actor allowlist 和原始来源/actor；按 command ID 与规范化输入指纹去重，同 ID 异文返回 `IDENTITY_CONFLICT`，重放返回原记录。
- 目标不再只做 Environment 授权：请求时用 `selectExecutionTarget` 的显式目标路径重新核验 Ticket 的 `local-only | remote-only | auto` 目标种类、actor allowlist、真实 probe 的在线状态/目录/版本/指纹、Instance Policy 权限、Ticket 必需能力和设备容量。目标不满足时持久化为 `target-ineligible` blocker，而不是绕过 T36/T38 的约束或静默换设备。
- 源目录来自 Assignment 固定的 Environment；源 probe 只补全缺少的 version/fingerprint。最新 T39 工作副本会被重新核验：必须为 `verified`，且 Assignment、源和目标身份与当前固定值一致；副本缺失、未核验或源在 prepare 后变化都成为 `handoff-blocked`。
- 安全边界要求 Ticket 为 open、无 constraint、无 stop、无 ready report、setup 未失败，且没有活跃 Worker turn、starting/running/cancelling/unknown 的后台 job、子 Agent 或 preview。`handoff-requested` 在接触任何执行范围之前先持久化；Worker relay 在 `requested/flushing/switching` 期间一律 defer，并在最终切换前再次检查活跃 turn。同一 Ticket 的并发交接请求在进程内串行。
- 原 job 的对账不靠猜测：任何 active/unconfirmed job 直接 `handoff-blocked`；可切换时记录已 settled 的 job ID 集合作为 `jobs-reconciled` 步骤证据，remote job 还要求 `rangeSettled`。仍处于 unknown 的范围不会被写成已静止。
- Session flush 使用 DSH 公开 Session 契约：有 live Agent 时调用 `sessions.flush`；没有 live Agent 时要求持久 Session 记录存在。flush 未确认时记录 `session-flush-failed` 并保持旧 Assignment，不切换。
- flush 之后重新核验目标与副本（`target` 选择、probe、目录/版本/指纹/容量、副本 verify），再进入切换；核验失败记录 `target-ineligible` / 工作副本 blocker 并保持旧 Assignment。因此目标在 flush 期间离线或身份变化不会被误报完成。
- 已存在未终结的 `requested/flushing/switching` 记录时，新的交接请求以 `HANDOFF_IN_PROGRESS` 失败关闭，不覆盖已持久化的进度；同一 Ticket 的交接在进程内也串行执行。
- 切换在单个事务内完成：重新检查 Ticket、Assignment ID/generation/state、活跃 turn 和新增后台工作；结束旧 Assignment；以同一 `sessionId`、新的 Assignment ID 与 generation 创建 pending 新代并绑定目标 Environment；释放旧 slot；把 intent 写为 `handoff-pending`；为携带 `environmentHandoff` 记录 ID 的 relay 入队；把 `completed` 记录与同 `commandId` 的 `work-command` 回执一起写入。失败返回 `handoff-stale`，旧 Assignment 不变；命令回执只随终态在同一事务提交，重放返回原结果而不是新建一次交接。
- 新代只允许交接 relay 先启动：在 slot 准入成功的同一事务里写 `promptStartedAt`，此前其他 input/status/job relay 继续 defer。新代收到显式的执行环境交接提示（源/目标目录、已核验副本、保留 Ticket/Mandate/Session），并要求先核对目录、版本控制和外部状态；不会把原始 trigger 文本重新追加为一条新请求，也不会重复已经完成的副作用。
- 交接提示不会静默丢失：该 turn 若在 setup 阶段失败，`promptStartedAt` 在同一事务里清除，`retrySetup` 会把同一条交接 relay 重新入队，未承接的工作得以继续。
- 轮次原因收敛为单个 `TurnCause`（`status | background | followup | environment-handoff | context-handoff | resume | launch`），准入激活级别和提示文本都由它派生，避免两处重复的条件链。
- 旧代继续由既有 Assignment ID/generation 校验隔离：旧 job、子 Agent、Input、foreground command、preview 和迟到回调不能唤醒或改写新代；同一 Ticket 始终只有一个有效 Assignment。

## 边界

- 实际文件传输仍是 T39 manifest 之后的显式同步；T40 重新核验已有副本并切换执行世界，不把路径字符串当成同一工作副本，也不做实时双写。
- 交接只切换执行 Environment；业务库、Session 存储、模型端点、授权范围和 Ticket 目标不搬迁、不扩大。running 不自动迁移，必须先有显式 handoff 命令。
- 有活跃或 unknown 的 job/subagent/preview 时直接 `handoff-blocked`，T40 不替代原有停止、取消确认和 unknown 对账流程；证明原执行范围静止是切换的前置条件。
- 每个持久步骤已保存稳定身份和进度，但 `requested/flushing/switching` 中断后的启动对账与继续属于 T41；T40 不声称已完成重启恢复，也不在未对账时继续相同步骤。崩溃在 `requested/flushing/switching` 时，重启后的 Worker relay 会继续 defer，直到 T41 加入对账/恢复入口，因此不会出现“完成标志缺失却开始双执行”。
- 目标和副本只在请求时核验；核验不是持续租约。请求之后的环境离线、Policy 变化或目录变化需要新的显式请求或按既有 T36/T39 blocker 处理。
- 未新增聊天 UI 入口；用户可见状态通过公开 Engine 查询和 `conversation` 投影提供。界面接入留给后续客户端/汇合票。
