## 已交付

### 1. 激活前 abandon

- 新增公开 `ds-superagent/reversal`：`Reversal.abandon`、`reverse`、`completeReverse`、`abandonment`、`reverseStatus`。
- `abandon` 只接受尚未 activation 的 batch。它先执行 T51 最终 `recheck`，要求 quiesced、blockers 为空、当前进程持有 gap entry，并扫描全部 gap input。
- `held` 或 `quarantined` 输入存在时返回 `blocked/GAP_OWNERSHIP_REVIEW`，旧入口保持停用，交由人工核查；`legacy-accepted` 是旧事实，不阻止。只有 gap 无待核查输入时，才把 switchover 记录标为 `abandoned`、释放 entry，并在提交后调用 `LegacyRecovery.enableRestart` 重新启用旧 launcher。
- abandon command 幂等；旧重启失败保留 `OLD_RESTART_FAILED` blocker，重试同一命令只重试重启，不覆盖 archive、其他 batch 或 staging。

### 2. 激活后 reverse handoff

- `reverse` 要求当前 activation 属于该 batch，并接受当前或更新的 Host epoch；它在一个事务里把 activation 置为 `stopping`、写 reverse manifest 与 command receipt，立即让 activation gate 失效，新 accept/Effect 返回 `CORE_NOT_ACTIVE`。
- 然后调用 `ReverseControl.stopAndSnapshot()` 停止新核心消费/执行/外发，并返回 durable evidence。evidence 包含 active turns/jobs/outbound、unknown effects/jobs、pending receipts、manual stops 和旧核心兼容性 blockers。
- 任一 active/unknown/pending/compatibility/release-pending 都使 reverse 保持 `blocked`；clear 后进入 `ready`，activation 为 `reversing`。reverse command 相同重试时复用原 manifest；Host epoch 前移会持久更新 reverseEpoch。
- `completeReverse` 在最终重新检查 Host owner/epoch 与旧核心 compatibility 后才允许重启；成功后 activation 为 `reversed`，reverse 为 `completed`，switchover 记录为 `abandoned`、entry 释放。旧 launcher 只被重新启用，不重放旧队列。
- 旧未完成/人工 stop/old review 保存在 reverse manifest 与 activation manifest；旧系统权限/格式/作业不兼容是显式 blocker，不会静默降级。

### 3. 真实/隔离演练

- `reversal.test.mjs`：无 gap 的 abandon 重新启用 launcher 并保留 batch-2 archive；held gap 的 abandon 阻塞；reverse ready 后 gate 拒绝新 submit；unknown effects、旧核心不兼容、real Engine pending outbound 都是 blocker；中断后同一 command 恢复；新 Host epoch 可 reverse；最终 compatibility 复查阻止重新启用。
- `reversal-process.test.mjs` + `reversal-crash.mjs`：真实旧 launcher/receiver、真实 activation、真实 reverse 子进程。activation 释放一个 held gap 到新核心；reverse 子进程写 stop marker 后退出；新 Host epoch 按同一 reverse command 恢复、旧 launcher 重新启用、旧 receiver 可再次启动；old receipts 仍为空（新核心的释放没有重放进旧队列），source state 不变。

## 使用方式

```js
const reversal = new Reversal(storage, instanceId, switchover)

await reversal.abandon({
  batchId, commandId: 'abandon-1', reason: 'Operator cancelled the switch.',
  legacy: oldCore, // includes stop/disable/restart/snapshot
})

await reversal.reverse({
  batchId, commandId: 'reverse-1', reason: 'The new core cannot continue.',
  control: { stopAndSnapshot: async () => newCoreEvidence },
})
await reversal.completeReverse({
  batchId, commandId: 'reverse-1',
  legacy: oldCore,
  compatibility: async () => ({ canReopen: true, blockers: [] }),
})
```

## 边界

- `ReverseControl` 由宿主实现：必须实际停止新入口的 turns/jobs/outbound，并按 evidence 返回持久事实；本票用真实 Engine 的 pending outbound 证明它会阻止 silent reverse，但没有把“停止所有执行”伪装成已在引擎内部自动完成。
- reverse 允许新 Host epoch，不搬业务库/Session；跨进程 gap entry 接管、真实 Electron 安装包、真实产品旧团队和用户数据迁移未运行。
- abandon 对 held/quarantine 选择保守阻塞，不自动把旧输入重放给旧核心；用户核查后仍需显式处理。
- 没有 UI；设置/迁移恢复界面留 T55。
