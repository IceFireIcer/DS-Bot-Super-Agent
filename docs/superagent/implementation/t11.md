- Issue：[T11 / #39](https://github.com/IceFireIcer/DS-SuperAgent/issues/39)。依据：规格 v2.1 D01/D08，A07/A39，用户故事 2、52、103；审计补充 F03。
- 固定实施基线：`b36e056`；实现提交：本票提交。
- 公开测试边界：`Engine.submit`、`receiveSource`、`acceptSource`、`conversation`、`listSlots`、`requestStatus`、`stopTicket`、Effects 派发/回执、`Slots` 契约，以及真实 Effects 与原生 DSH Router/Worker Session 的 mock 集成。未使用真实模型、外部账号或用户 DSH 数据。

## 行为

每个 Worker 回合持有一个持久执行槽，覆盖目录准备、启动、唤醒、活跃回合：`prepare` 到 `turn` 的推进与释放都在回合的事实事务内提交。槽按 Assignment 归属，两个 Ticket 不会共用，也不会串用彼此预算；`listSlots()` 返回声明的 `limits`、持有槽（含 `priority`、`activation`、`phase`）和排队槽（含 `SLOTS_FULL`/`PRIORITY_WAITING`），`conversation(ticketId).slot` 同时给出单票视图。

普通启动使用正常预算（`maxSlots`，默认 2）。人工跟进、状态请求与恢复可用一个有界额外槽（`maxPrioritySlots`，默认 1）。额外槽只是溢出：正常容量有空时新准入仍占正常槽，因此优先持有数量不会超出自身上限。人工跟进越过排队启动，突发自动事件不能长期饿死人工输入；有优先准入在等时，新启动报告 `PRIORITY_WAITING`。队伍满时 Ticket 的 intent reason 为 `slot-queued` 或 `slot-priority-waiting`，查询可直接看到排队与占槽原因。

Effects 按 lane 独立派发：一个慢 Worker 回合只推迟自己的 lane，pass 直接跳过仍在运行的 lane，后到的工作不会排在其后；释放槽会唤醒派发，不必等下一次周期扫描。等待槽的 relay 返回 `defer`，不消耗重试预算。`requestStatus` 是受限命令：只对已结束回合且无 result 的空闲 Worker 生效，stop、waiting-human 与从未运行过的 Ticket 都会被拒绝。状态回合只拿到一个 `report_status` 事实工具，不提供 `report_ready`、`ask_human` 或订阅工具，因此不能报 ready、提问或改订阅；记录的文字进入 `conversation(ticketId).statusReport`，不构成结果。

ready、waiting-human、stop、idle 与异常退出都会释放槽；回合主体包在单一 `try/finally` 中，任何提交后异常也不会留下占槽。上一个 runtime 遗留的持有或等待记录不能被证明仍存活，新 runtime 首次读取时会删除，避免旧 Host 的账目永久占满新预算（此时 Ticket 的 intent reason 仍是排队，直到 relay 重新取到槽）。

## 验证

```sh
cd superagent
npm run typecheck
npm test
npm run lint
npm run build
node dev/slots.mjs
```

2026-11-07，Windows x64 / Node 25.4.0：新核心全量 **130/130** 通过，typecheck 与 lint 无错误。T11 定向覆盖两条独立 Ticket 同时推进且慢任务只延迟自身、正常预算满时人工跟进使用有界额外槽并越过排队启动、突发自动启动不能让后续人工输入排队、`requestStatus` 仅限空闲 Worker 且状态回合只有 `report_status`、状态事实可查询而不构成结果、槽按 Assignment 归属、优先槽位上限、跨 runtime 的旧持有清理，以及同源 chat 入口的 `/slots` 与 `/status`。`node dev/slots.mjs` 在声明负载（2 正常槽、1 额外槽、6 票、400 ms mock 回合、50 ms 扫描）下连续三次实测：并发 Worker 回合峰值均为 3（符合 2+1 上限），4 票排队等槽，人工跟进约 4 ms 内在额外槽开跑而 4 个启动仍在排队，全部启动在约 2030—2080 ms 内完成（公平性预算 3600 ms）。

## 边界

本票验证并发准入与人工优先，不实现后台长命令/子代理（T12/T13）或交付验收时的槽释放与预览服务（T14），也不代替 T54 的性能比较。并发槽与效果派发的实测数字来自确定性 mock 负载，不是真实模型吞吐或生产 SLA。Schedule/query 视图目前由 `listSlots`、`conversation` 与 intent reason 提供；真实来源信道、真实模型与第二设备验收仍待对应票。

同分支工作树还带有 T09 的 `recoverStaleStop` 提取与 `test/stop.test.mjs` 回归、以及本票新增的 `TURN_ACTIVE` 守卫；它们属于 T09 行为，随本票一并提交，在 PR 中单独说明。
