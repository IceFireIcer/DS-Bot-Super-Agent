## 公开关联入口

```js
const reference = await owner.getTicketReference(ticketId)
// 将 reference 原样放进由受信 receiver 接收并核验的原生 PR/comment/review 正文。
const linked = await owner.associateSourceEvent({
  commandId, ticketId, eventId, reference,
  reason: 'The original owner approved this exact native correction.',
  retargetResult: true,
}, githubEngine)
// linked: { input, target? }
```

引用格式为 `superagent://<encoded Instance>/tickets/<encoded Ticket>`，它是关联证据，不是访问凭据。命令必须由原 Ticket 受信来源的原始 actor 发起；接收 Engine 必须同 Instance。接收 actor、scope、当前原生版本、独立配置的人类作者准入和 direct/mention 寻址分别核查；正文必须只有一个唯一完整目标引用。相似主题、错误/多个目标、删除/冲突/旧版本、机器人和无权作者均不能串线。

单个异步事务保存稳定 Input、显式 ownership、关联依据、方向增量、relay 和可选结果目标。`input.association` 保存完整来源、原生作者、原始授权 actor、引用、理由与时间。原 Ticket/Mandate/Assignment/Worker/Session 保留；stop、人工等待和来源暂停不能被绕过。

读取隔离以 Ticket 原 trigger 的精确来源 actor 为边界。即使另一个 Engine 使用相同 Instance/source instance，且自己的 actor 出现在其配置 allowlist 中，也不能直接猜 Ticket ID 读取；`listTickets` 同样过滤不可读对象，并以有界、来源安全的 opaque cursor 继续扫描。cursor 是进程内 5 分钟、最多 100 个的 token，绑定来源 actor；Host 重启会使 cursor 失效但不暴露原生 Ticket ID，调用方重新从第一页开始。已知引用只作为关联证据，不授予访问权。送达目标若引用 evidence event，不论同来源或跨来源，都重新核验该事件仍为 current 且作者仍获当前 Policy 授权。等待问题、Attention 和 answer 的 Outbox 同样在发送前复核问题事件 current 与收件人授权。

本切片只承接被显式核验的事件，不自动订阅整个外部 Thread。后续事件仍需独立 owner 授权；同名用户不自动合并。原 `attachSourceEvent` 保持隔离，外部 Engine 不因引用获得私有 context、搜索或无关 Thread 历史。

## 问题、回答与改投

- 确认回原始消息；关联输入触发的 Attention 回那条原生事件的来源、Thread、对象和作者，Outbox 必须逐项匹配持久关联。
- 原始 owner 可调用 `owner.answerAttention({ commandId, attentionId, text })`，以自己身份明确回答，不冒充 GitHub 作者。
- 原生回答使用 `owner.answerAttention({ commandId, attentionId, text, sourceEventId }, githubEngine)`，重新核验当前原生事件、scope、作者与问题收件人，正文来自原生事件。新 Input 保留关联依据，继续原 Session。
- `queueAnswer` 只能回答精确合法承接的问题，Outbox 复核当前版本和收件人；结果改投不广播问题或回答。
- 关联默认不改投；`retargetResult: true` 使用同一事件证据。旧 `setDeliveryTarget` 在 versioned source 或跨来源目标上必须引用合法关联且当前有效的原生证据；只有无 native source event 的 direct trusted owner 命令仍由当前 source actor 自身授权。
- Outbox 执行前复查关联、当前证据和持久来源策略。永久不可达/未授权记丢弃，不自动改回桌面或另一讨论。
- 共享 `answerFromSourceEvent` 在作者授权后核对 `sourceEvents.candidate(tx, event)?.id === event.id`；旧/冲突事件不能自动解除 Attention。该 guard 由本任务协同集成，未修改 Feishu 模块。

## 实际 GitHub outbound adapter

```js
const channel = new GitHubDeliveryChannel(new GitHubCliReplyTransport(), {
  storage, instanceId,
  sources: [{ sourceInstanceId: 'github:acme/repo', host: 'github.com',
    owner: 'acme', repo: 'repo', actorId: 'authenticated-posting-login' }],
})
const platform = await channel.getReceipt(idempotencyKey)
```

`GitHubCliReplyTransport` 通过公开 `gh api` REST 读取认证用户，核验精确原生目标，分页读取讨论评论并发送评论。POST 使用 stdin JSON；不拼 shell，不输出凭据/正文/原始 CLI 错误。来源、服务地址、仓库与 posting actor 显式配置；认证账号不匹配时在 POST 前拒绝。

首次 POST 前在现有 `work-command` 持久保存出站身份及内容/目的地摘要。正文附加 Instance/idempotency key 派生的 SHA-256 marker。丢响应只按原 marker、完整正文、认证作者和平台 URL/ID 对账；不盲重发，不声称 GitHub 提供事务 exactly-once。重放复用回执，异文/异目的地拒绝，并发 claim 不二次 POST。

`getReceipt()` 返回持久 message ID、URL、来源、Thread、marker 与时间；sent 必须有可核查平台身份。全文超过 60000 字节拒绝而不截断；对账最多 10 页/1000 评论，真实 CLI 单请求最多 30 秒且继承取消信号。扫描超限、伪造/重复 marker、未知响应保持 unknown；永久失败不换目的地。SQLite/PostgreSQL 共用已有异步存储契约/记录类型，无新 schema、私有 DSH API 或用户数据访问。

## 边界

### 对账脚本及评审后修复（2026-11-11）

父任务报告实际结果已 POST/读回但末尾对账失败。本任务本地 Engine/Outbox + mock transport 复现：`getTicketDeliveries()` 是历史序列，首条 result 是改投前桌面记录，后续才是实际 GitHub 记录；两者共用 Effect ID/generation，所以正确的 JSON array key 仍能找到平台回执。将首条桌面历史传给 GitHub channel 的精确错误是 `DESTINATION_DENIED`，不是字段顺序或 fingerprint。脚本改取 `conversation.messages` 当前结果，保留 `JSON.stringify([effectId, effectGeneration])`。失败输出只包含限定 reason code、类型和平台消息 ID。

新增公开 Engine→Outbox→getReceipt→reconcile 回归先红于 `permanent/DESTINATION_DENIED`，修正选取后通过；核验实际 outbound destination/text 与查询结果一致，POST 总数保持 1。未因排查再做外部写入，不额外保留临时数据。

handback 后新 command 现检查 inactive ownership 并拒绝 `OWNERSHIP_INACTIVE`；原 command 仅 replay 原回执，不更新目的地。测试/真实脚本清理按序尝试所有资源再汇总异常。共享 `receiveUnverifiedSource()` 原子存储 opaque 未核验观察及 unknown projection，不触发 fan-out/自动回答；旧正文不能继续关联。原 owner 撤销执行授权后仍可读自身历史，跨来源私有读取仍拒绝。
