- Issue：[T15 / #43](https://github.com/IceFireIcer/DS-Bot-SuperAgent/issues/43)。依据：规格 v2.1 D09/D13，A10/A21/A31，用户故事 60、92。
- 固定实施基线：`36e62a5`；实现提交：本票提交。
- 公开测试边界：DSH 公开 `SessionPersistence`/`SessionHandle` 契约与 `session/created`、`session/event`、`session/flush`、`session/disposed` 生命周期，公开 `ctx.agents.create()`/`resume()` 原生 Agent loop，`NativeSessions` 与 mock 模型的原生集成，以及真实 DSH fork（`ctx.sessions.fork`）。未使用真实模型、外部账号、第二设备或用户 DSH 数据。

## 行为

新的 `session-persistence-sqlite` 插件实现 DSH 公开的 `SessionPersistence` 服务，并把 Session 头、连续事件日志与 writer 记录写进与业务数据同一个 SQLite 事务工作线程（`instanceId: 'session-store'`）。记录种类是 `session-meta`、`session-event`、`session-writer`：事件键用补零 seq 排序，因此扫描顺序就是 Session 序列顺序，序列不连续会在写入前被 `assertContiguous` 拒绝；头用 `materializeCreateHeader`/`assertVersion` 校验格式版本（4）与 id 一致性，读回时用 `validateStoredEvents` 复核整段日志。`open(id, 'read')` 只读，`open(id, 'write')` 在授予写权前校验既有日志、并只在没有活动 writer 时才成功，否则抛 `SessionAlreadyOwnedError`。fork 通过 `create(header, { inheritedEventCount })` 保留 `parentSession`、`isSeeded` 与继承前缀，读回时 `inheritedEventCount` 与头一致。`stat`/`list` 提供轻量的头、revision 与逻辑事件数，供调用方决定 resume 还是 create。create 后从未 append 的 Session 在 close 时删除自身 meta/writer 记录，与 JSONL 后端“未物化 Session 无存储足迹”的行为一致，因此发布前失败不会留下空 Session 让下次误 resume。

唯一 writer 由 `session-writer` 记录守卫，记录里带单调递增的 `epoch`、活动标志与 owner PID。每次 `append`、`flush`、`close` 都在同一事务里重读该行并比对 `epoch` 与活动状态，不匹配即抛 `SessionOwnershipLostError`：被替换或崩溃恢复后的旧 handle 不会静默重新获得写权。`open(id, 'write')` 对仍 active 的行先探测 owner PID 是否存活；进程已死（crash，无优雅 close）时以新 epoch 接管，活进程则抛 `SessionAlreadyOwnedError`，与 JSONL 后端“内核锁随进程退出释放”的语义对齐，崩溃的持有者不会永久阻塞后继。`append` 每次调用就落盘，因此 Agent loop 在 publish 前经 `appendUnstoredSuffix` 写入的构造后缀是持久的。`flush` 先排空 live 队列，再提交一次 revision 更新；提交失败时写权仍归本 handle，可以继续 append/flush。`close` 只有在持久写入成功后才释放 writer 行并移除进程内路由；持久失败时 handle 保持打开和持有写权，不会伪报已关闭。服务级 `flush()` 排空所有打开写 handle，任一失败用 `AggregateError` 报告，但不释放任何一个。

接入原生 Agent loop 时，`apply` 把 `session/event` 路由到当前写 handle 的有序 append 链，`session/flush` 映射为 `handle.flush()`，`session/disposed` 触发最终排空与释放。因为 loop 在 `prepared.publish()` 之前 `await appendUnstoredSuffix(stored, session)`，而 provider 的 `append` 每次调用就是一次持久提交，构造期与恢复期（含 `session/end-seed` 与 interrupted-turn closers）的记录在 `session/created` 广播时就已可读，不是只靠监听后续 live 事件补齐。这满足并强于“flush 后再 announce”：没有待刷新的缓冲，且写入失败会让 `appendUnstoredSuffix` 抛错，发布不会发生。`NativeSessions` 不再维护进程内的 `completed` 集合，而是用公开 `stat()` 判断是否存在持久 Session，决定 `resume()` 还是 `create()`，因此适配器替换或进程重启后仍能恢复同一 Session 历史。

2026-11-08，Windows x64 / Node 25.4.0：新核心全量 **187/187** 通过（T15 新增 22 项：provider 15 项 + 原生集成 7 项），typecheck 与 lint 无错误。T15 定向覆盖：

- provider 契约：唯一 writer、连续序列、读回校验、`stat`/`list`、只读句柄拒绝 append、重复 create 拒绝。
- writer 守卫：注入 flush/close 持久失败后仍保有写权并可继续写入；writer epoch 被推进后旧 handle 的 append/flush/close 全部抛 `SessionOwnershipLostError` 且不重获写权。
- 服务级 `flush()`：排空所有打开写 handle 并推进两个 Session 的 revision；注入失败时用 `AggregateError` 报告且不释放写权。
- 并发交错：两个 Session 各四次交错 append 后各自 seq 仍连续 `0..3`、事件数正确。
- fork：种子子 Session 保留 `parentSession`、`isSeeded`、`inheritedEventCount` 与继承 cut 标记。
- 回滚与格式：create 后从未 append 的 Session 在 close 时删除自身记录，不留空 Session；显式 flush 过的空 Session 会保留，不能被误删；未知事件类型、事件数不符或序列有缺口的存储日志在获得写权前被拒绝为损坏。
- 原子性与 live 失败：append 在单个事务内写入事件与头游标，中途失败不留下部分事件并可整批重试；live append 失败后 handle 停止接收新事件，flush/close 报原始错误而不是静默丢弃后续事件。
- 服务替换：替换后端拒绝活动 writer；原上下文 dispose 并释放后新后端才取得写权，继续读到既有事件并续写；旧 handle 只报已关闭，不重获写权。
- 崩溃恢复：真实子进程创建并写入 Session 后直接退出（无 close），父进程的新后端探测到死 PID 后以新 epoch 接管并续写。
- 原生生命周期：替换适配器后 resume 同一 Worker（构造与 live 历史连续）；取消后保留可恢复的中断历史与恢复标记；存储日志停在未关闭回合时，resume 在公告前补存 `step/end` 与 `reason.kind: 'interrupted'` 的 `turn/end`；经真实 `ctx.sessions.fork` 的 DSH fork 通过 SQLite 保留继承前缀与血缘；种子 Session 在 `session/created` 广播前其构造记录（含末尾 `session/end-seed`）已可从持久存储读到，且 seq 与写入的 seed 完全一致。
- 发布屏障：setup 在发布前失败，或构造后缀写入持久失败时，`session/created` 不广播、不留下已存 Session，同一 id 可重新创建；append 自身完成持久 checkpoint，因此构造后缀在广播前已过 flush 屏障。

## 边界

本票只交付 Session 持久化与恢复，不改变业务层（Ticket/Assignment/report/job 等）的持久化语义，也不跨票替代 T54 的性能比较或外部交付验收。业务持久化与 Session 持久化在报告中分开：业务事实仍由既有 store 记录，Session 事件日志由本 provider 记录，两者共用一个 SQLite 事务工作线程但各自独立查询与校验。writer 存活判断使用本机 PID，适用单机 SQLite 部署；若 PID 被无关进程复用，可能把已死持有者误判为存活（拒绝接管），不会造成双写，因为 epoch 守卫仍会拒绝旧 handle。跨机器共享数据库不在本票范围。真实模型、外部信道与第二设备仍待对应票；本票无界面改动，验收入口是公开 Session 契约与 `NativeSessions`，因此不附界面证据。
