## 交付行为

`engine.retryTicket({ commandId, ticketId, reason })` 为同一 Ticket 创建新的 Assignment 代次。它保留 Ticket、Worker Session 和绑定的本地目录，结束旧代，换用新的 Assignment ID 与 generation，并写入 `retry-decision`：旧代、新代、Session、目录、请求人、原因及四条恢复核查说明。`conversation(ticketId)` 返回 `retryHistory` 和最新 `recovery`。

恢复提示要求 Worker 先检查保留的 Session 与工作目录、比较版本控制状态、按原平台 ID/作业 ID/marker 对账外部副作用，并继续遵守 stop、waiting-human 与撤权。旧 ready report 在换代时不再作为当前报告，`conversation.reports` 为空；报告历史仍保留。Outbox 也拒绝属于旧 Assignment 的报告，即使它的 ID 仍可查。

以下情形拒绝创建新代：

- 当前 Assignment 仍有本进程的活动回合。
- Ticket 处于 stopped 或 waiting-human。
- Effect 存在 unknown 外部结果。
- 验收预览清理仍未确认。
- 旧 Assignment 的 job/subagent 仍为 running、cancelling 或 unknown。

被未知作业阻塞时，`retry-decision` 与 `recovery-blocked` 状态仍会提交，`recovery.blockedWork` 列出原作业 ID 与状态；重放同一命令返回同一阻塞结论。迟到 job/subagent 回调继续按 Assignment ID 与 generation 判定 stale，旧报告、旧 Effect 与旧完成事件都不能推进新代。

## 验证与范围

2026-11-09，Windows x64 / Node 25.4.0：新核心全量通过，typecheck、build、lint 通过。

新增回归覆盖：

- ready 后显式 retry：新代、同 Session、同目录、旧报告不再当前、报告历史保留、新 Worker 收到恢复提示并产出第二份 ready。
- unknown Effect、旧 running job、stopped Ticket 分别阻止 retry；未知作业会留下 `recovery-blocked` 证据。
- 既有 T12/T13 迟到 job/subagent、T16 未读输入、T09 stop/resume 回归保持通过。
