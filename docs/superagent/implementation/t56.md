## 已交付

- `superagent/src/ds-bot-host.ts` 提供 production factory：
  - 一个共享的绝对 SQLite 业务库；
  - 每个 UI Session 一个 `Engine`、一个 `NativeSessions` 和一个绑定 Session；
  - 原生 Agent 日志继续使用 Host 的公开 `sessionPersistence` 服务；
  - Engine 的 Session/Instance、Effects、delivery 和 host lease 由 factory 生命周期管理；
  - 缺少数据库路径、路由或 Host Session provider 时启动失败。
- `ds-bot-host` Cordis 插件把 adapter 发布为 `botExecutionAdapter`，并在 Host dispose 时关闭 adapter、每个 Engine、Effects 和 NativeSessions。
- `ds-bot/src/host/execution-adapter.js` 优先使用配置的 adapter，否则读取可信 Host 服务 `botExecutionAdapter`。profile 可设置 `executionAdapterRequired: true`，此时没有 adapter 会明确失败，不再静默走旧路径。
- `DsBotExecutionAdapter` 新增：
  - `close()`：幂等关闭所有 scope，清理错误用 `AggregateError` 返回，关闭后拒绝新工作；
  - `resolveAgent()`：为现有 UI Session 返回兼容 facade，映射 `followup`、`cancel`、`status`、`whenIdle` 和空 inbox；group/steer 仍 fail-closed；
  - `chatPage()` 在“prompt 已持久确认、Worker Session 尚未物化”的窗口返回空页，避免 UI 首次轮询报 `NOT_FOUND`。
- `ds-bot` 保留现有 `/api/bot`、SSE、session/chat、question、delivery、resume 形状；没有修改 `app/ui/`、`ds-bot/src/client/` 或 `ds-bot/client.js`。

## 测试证据

### 真实 Host 进程

`superagent/test/fixtures/t56-host.mjs` 在独立 Node 进程中：

1. 启动真实 DSH Context 与 mock provider；
2. 加载 `ds-bot-host` profile 插件；
3. 通过真实 `ds-bot` 的 `install()` 和 `executionDispatch()` 完成 prompt、deliver、`resolveAgent` 和 stop；
4. 关闭 Context 后，第二个进程重放同一 requestId，得到同一 Ticket、同一组 Session 事件序和相同用户消息数，没有重复建工作。

`superagent/test/t56-host-process.test.mjs` 断言两次进程退出均为 `0`，Ticket/交付身份一致，并覆盖 stop 进程。

## 边界

- **真实模型、GitHub/飞书真实信道**由 T57 验收；本轮 delivery 使用本地账本，不能称为平台回执。
- **app profile 的依赖/打包 wiring**、托管 Host、断连/撤销/接管和第二设备组合由 T58 验收。T56 已提供 profile 插件、服务 seam 和真实 Host 进程组合，但未把 `ds-superagent` 打进桌面安装包。
- UI 关闭/重连和完整桌面端到端仍由 T58/T55 汇合；本轮没有修改桌面 UI。
- group、browser、view、attachment、steer 仍 fail-closed；`resolveAgent` facade 的 inbox 为空，不把 Engine 内部 Worker 队列伪装成旧 DSH inbox。
- 本地 SQLite 业务库和 Host 的 Session provider 是两个持久面；本票不声称两者具有同一备份/恢复边界。
- `ds-bot` smoke 未运行：当前环境没有 `../deepseek-harness` checkout，`DSH_HARNESS` 也未设置；这是环境缺口，不是本票通过证据。T58 的部署组合仍需补跑适用 smoke。
