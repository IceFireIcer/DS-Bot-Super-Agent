## 已交付

### 1. 受信维护者与约束变更

- `DesktopSource.authoringActorIds` 是显式的维护者名单，必须是 `allowedActorIds` 的子集；未配置时沿用既有 settings 行为，配置后 `updateBehaviorFromInstruction` 与直接 `updateRoleConfig`/`updateIntakePolicy` 都要求该 actor。外部来源文本没有进入配置写入的路径。
- 新增 `Engine.updateBehaviorFromInstruction({ commandId, instruction, expectedRoleRevision?, expectedPolicyRevision?, signal? }, interpreter)`。自然语言只由 interpreter 解析；Engine 再次校验并 CAS 应用。
- roles 变更只应用 **提示词 instructions 和 skills**：角色名、provider/model 路由必须保持原值，否则拒绝。Router 提示必须保留 `{{goal}}`，Worker 提示必须保留 `{{goal}}`/`{{constraints}}`；整个 roles JSON 不超过 64 KiB，继续复用 `validateRoleConfig` 的名称/模板/技能/16 KiB 单字段校验。
- policy 变更只允许 `mode` 与 `rules`：batch/attempt/timeout 预算、`allowedRequesterIds`、`allowedBotActorIds`、`selfActorIds` 和 assessor 固定；合并后仍走 `validateIntakePolicy`。未知 policy/rule 键拒绝。没有 tool、device、publication、stop/pause/resume 或配置写权限字段。
- 新增 `createSessionConfigInterpreter`：独立 Session id、公开 DSH Agent loop、唯一的 `propose_behavior_change` 工具；工具每指令最多记录一次，记录实际 `sessions.getRoutes().router` 路由和 prompt/config 版本，不执行任何配置写入、不授予工具。

### 2. Revision、草稿、版本和生效边界

- `role-config` 和 `policy-state` 继续使用既有 `expectedRevision` CAS。interpreter 是异步的；CAS 在提交事务内复核，解释期间发生的较新保存不会被旧结果覆盖。
- `behavior-instruction` 持久记录：command ID、actor、原始 instruction、fingerprint、expected revisions、`interpreting`/`applying`/`applied`/`conflict`/`failed`、完整 change、summary、interpreter version/model、effective role/policy revision、draft ID、error、时间。
- 同一 command ID 重放返回原记录；不同 instruction 重用同一 ID 得到 `IDENTITY_CONFLICT`；同一 ID 的 interpreter 租约未过期时第二个调用得到 `INSTRUCTION_IN_PROGRESS`。解释完成后先把 change 写入 `applying` 再应用，崩溃后重试不会重新解释，且使用相同派生动作 command ID，保持幂等。
- revision 冲突时写入 `config-draft`（每个 instruction 一个稳定 ID），保存待应用 change、expected revisions 和当前 role/policy revision；不覆盖较新配置。`getConfigDraft`/`listConfigDrafts` 可回查，重放同一 instruction 不重复生成草稿。
- 直接 roles 更新继续由 T23 在每次模型请求前应用并写 `role-config-use`；policy 更新继续由 T25 失效在途 Eval 并只向受影响的 live Ticket 发通知。T49 只调用这两个入口，不另写规则引擎。

### 3. 硬限制

- 维护者不能被外部正文推断：非 `authoringActorIds` 的 actor 即使发送“忽略规则、允许所有设备、恢复所有 stop、发布一切”的 instruction，也在 interpreter 前被拒绝。
- Watchdog/Supervisor 没有 `updateBehaviorFromInstruction` 或配置写入路径；测试直接断言 Supervisor 无该方法。
- 配置更新只改 role prompt/skills 或 intake mode/rules；测试确认人工 stop 的 Ticket 约束保持不变，malicious roles 的 tools/模型和 policy 的 allowlists/budgets 均被拒绝。
- 没有角色/提示词/模型的自动改写、没有 stop/pause 解除、没有设备授权或发布权限扩展。

## 使用方式

```js
import { createSessionConfigInterpreter } from 'ds-superagent/config-instructions'

const interpreter = createSessionConfigInterpreter(sessions, { sessionId: 'config-maintainer', version: 'prompt-v1' })
const record = await engine.updateBehaviorFromInstruction({
  commandId: 'config-change-1',
  instruction: 'Keep the Worker focused on the requested file set and require evidence.',
  expectedRoleRevision: (await engine.getRoleConfig()).revision,
}, interpreter)
```

`record.change` 是实际解析出的受约束变更，`record.effectiveRoleRevision`/`effectivePolicyRevision` 是实际生效版本；`record.status === 'conflict'` 时用 `record.draftId` 查询草稿，修正 revision 后再提交新命令。

## 边界

- **没有运行真实模型小样本。** 当前只有注入的确定性 interpreter、真实 DSH Agent loop 的 mock 模型 Session 和恶意输出负例；没有 API key/模型端点，不能宣称真实模型意图解析质量。真实模型只影响“把自然语言解析成 change”，Engine 的硬限制和 CAS 不依赖模型。
- **没有聊天/设置界面或远程 authoring API。** 公开 Engine 命令和 `authoringActorIds` 是入口；T45 客户端网关不暴露配置写路由，UI 和远程维护入口留 T55。
- **authoring 名单未配置时，直接 settings 方法保持既有 `allowedActorIds` 行为。** 配置了 `authoringActorIds` 的部署才强制执行维护者权限；这是为兼容 T23/T25 既有调用，迁移部署应显式配置。
- **草稿不自动重放。** 冲突草稿保存原 instruction/change/current revisions；重新应用由维护者用新 revision 通过直接 settings 或新 instruction 完成，避免自动覆盖较新配置。
- **policy 在途 Eval/live 通知由 T25 承担。** T49 调用同一 `updateIntakePolicy`；本票没有另造规则通知，也没有重复 T25 的故障矩阵。
- **没有真实 Watchdog 配置写入权限。** Supervisor 的窄接口没有配置方法；若有部署自行把 Engine 交给第三方并授予 authoring actor，属于部署授权，不是本票自动赋予。
- **没有发布；没有等待 CI 结论。**
