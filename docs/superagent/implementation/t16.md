# T16：重启后恢复未处理输入而不重复追加历史

- Issue：[T16 / #44](https://github.com/IceFireIcer/DS-Bot-Super-Agent/issues/44)。依据：规格 v2.1 D05/D09/D13，A10/A31，用户故事 60、69。
- 固定实施基线：`970a0a4`；实现提交：本票提交。
- 公开测试边界：`Engine.getTicketDirection`、`conversation`、`effects.start`/`drain`，`WorkInput`/`InputDelivery` 契约，真实 DSH Worker Session、公开 `SessionPersistence` 日志读取、SQLite 业务/会话库，以及真实隔离子进程退出。未使用真实模型、外部账号、第二设备或用户 DSH 数据。

## 行为

每条跟进 Input 现在带一组可分别查询的持久投递事实：接收/归属由既有 `work-input`、`work-ownership` 与方向版本记录；`delivery.claimedAt` 是发送前在同一事务取得的 claim（含稳定 `messageId`、Assignment 与 Session），`delivery.sentAt` 是交给原生适配器的尝试，`delivery.persistedAt`/`persistedMessageId`/`persistedSeq` 只在 Session 的 `user/message` 已进入持久历史并**通过 flush 屏障**后写入，`delivery.completedAt`/`outcome` 在 Worker 真正承接工作（ready、waiting-human 或 handback）的**同一事务**写入——`report_ready`、`ask_human` 与 `handback_input` 都在各自的验收事务里完成该 Input，崩溃不会留下“已验收但 Input 仍 pending”的窗口。普通 idle 回合不写 `completedAt`，Input 保持 `pending`，因此“已持久投递”不会被显示成“模型已处理”。

`messageId` 由 Input ID 确定性派生，首次 claim 时写入并跨重启复用。Worker 发送前先用公开 `SessionPersistence` 读取该 Session 日志：原始消息已在历史中时不再追加同一条用户消息，而是以恢复说明启动新回合（先核查 Session 历史、文件、版本控制和外部状态，再继续原请求）；未入历史时按**原 `messageId`** 重发原消息。`NativeSessions.run` 接受显式 `messageId`，并在收到对应 `session/event` 后先 `sessions.flush()`，再回调 `onMessagePersisted`；flush 失败不会写持久回执，本轮也不会被当作已投递。

未完成 Input 由独立的、可分页的 `pending-input` 索引维护（创建 Input 时写入，完成或耗尽时移除）。启动扫描逐页读取索引，不把历史 Input 总量算进预算；单个 Input 的失败只记录警告并继续后续项，不会让整轮恢复中止。扫描只处理仍然 open 且无 constraint 的 Ticket，并核对 `work-ownership`：已 `handed-back` 的 Input 记为 handback 完成，已 `requeued` 或不再 owned 的 Input 标记耗尽，绝不会把刚交回的消息重新 attach 给同一 Ticket。`Effects.start()` 把该扫描作为可等待的 pass 加入生命周期，`drain()` 会先等待它、`stop()` 也会等待它结束，然后才开始常规派发，因此重启后先确定未读/已读边界，不会在扫描前用旧 inbox 副本抢跑或与关闭过程竞争存储。

恢复回合沿用原 Ticket 与 Session，但若之前已有 claim 则创建新的 Assignment 代次（同一 `sessionId`），避免把崩溃前的执行归属当成当前归属。恢复说明带尝试序号并作为新的用户消息进入历史，正文要求先核查 Session 历史、文件、版本控制和外部状态；原用户消息不会再次追加。恢复回合最多 3 次，Input 的总投递尝试最多 5 次，超过后写 `exhaustedAt`、把 intent 标为 `recovery-exhausted`，不会无限重试。relay 处理同时实现 `reconcile`：崩溃后处于 unknown 的 relay 会重新执行，而 Worker 在发送前重新读取持久 Input/Session 边界，因此重跑只会续传而不会重复追加原消息。


2026-11-08，Windows x64 / Node 25.4.0：新核心全量 **194/194** 通过（T16 新增 7 项），typecheck 与 lint 无错误。T16 定向覆盖：

- 真实子进程在 claim 前退出：重开后 Input 无 delivery，恢复按原 messageId 发送一次并完成，历史中该用户消息恰好一条。
- 真实子进程在 claim 后、append 前退出（`sentAt` 已作为发送尝试记录）：重开后保留 claim/sentAt、无 persistedAt；恢复按原 messageId 发送一次，不重复。
- 真实子进程在 append 后退出：重开后能从公开 Session 日志读到该 messageId；恢复不再追加原消息，改用恢复说明继续。
- 真实子进程在 Session provider 的 flush 注入失败后退出（不是替换 SessionStore）：persistedAt 未写，但日志已有该消息；恢复不重复原消息，改用恢复说明并最终完成。
- 真实子进程在持久回执后退出：重开后 persistedAt 已存在；恢复同样用恢复说明继续，原消息仍只有一条。
- 进程内 idle 回合：persistedAt 写入而 completedAt 为空、state 仍为 `pending`；重启后的启动扫描发送恢复说明，原消息不重复，最终 `state: delivered`、`outcome: ready`。
- handed-back：Worker 交回 Input 后 ownership 为 `handed-back`、Input 已交付；重启扫描不会为它排新的 relay，也不会把消息重新 attach 给同一 Ticket。

CI 的 Linux Node 22.19/24 运行还暴露了一个既有的评估扫描缺陷：`SourceEvaluations.runNext` 先把 `eval` 扫描结果映射成值再读取 `id`，当扫描页包含无 `id` 的 `head:` 记录时会抛 `startsWith` 错误。该错误会让 after-claim 窗口的 turn 在 claim 后静默中止。修复为按扫描条目的 key 前缀过滤后再取评估值，并保留真实子进程的固定退出窗口；这不是 T16 的行为扩展，但恢复验收依赖它。

共用基准未出现回归：`node dev/jobs.mjs` 在声明负载下回合在约 188–397 ms 返回（命令仍运行）、方向取消约 28–37 ms、完成事件约 438–524 ms、退出码 0 且不构成结果；`node dev/subagents.mjs` 父回合约 195–199 ms 交出控制、4 个子任务并发完成（共约 74–106 ms）、子工具仍只有 5 项本地工具；`node dev/slots.mjs` 峰值 3（2 正常 + 1 人工额外）、6 个启动在约 1917–2337 ms p50 内完成、公平性预算 3600 ms。以上是确定性 mock 负载与真实 DSH Session 的开发测量，不是生产 SLA。旧插件 `ds-bot` 单测 1431 通过、2 跳过、0 失败；客户端生成一致性与 lint 通过（保留既有警告）。

## 边界

本票只恢复 Worker 的**跟进 Input**，不改变初始请求的投递路径；初始 trigger 仍由接单事务和原生 loop 直接启动。恢复说明会作为新用户消息进入 Session，这是“已入历史不重复追加原消息”与“继续未承接工作”的最小取舍；原消息不会被改写或删除，每次恢复说明都带尝试序号，恢复消息与原消息都可逐条查询。恢复最多 3 次、总投递最多 5 次，避免磁盘持续故障导致无限回合；超过后保留 `exhaustedAt` 供人工核查。通知/结果的 Outbox 回执仍按 T02/T10 规则处理，本票不新增跨平台 exactly-once。真实模型、外部信道、第二设备与界面验收仍待对应票；本票没有界面改动。
