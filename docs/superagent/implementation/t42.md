# T42：用 PostgreSQL 完成同一领域命令与提交对账

- Issue：[T42 / #70](https://github.com/IceFireIcer/DS-Super-Agent/issues/70)。
- 实施基线：`2aecada`。
- 规格：v2.1 D03、D10、D13；A01、A11、A12、A18、A32、A44；用户故事 60、72、74、93、108。审计补充：F08。

## 已交付

- 新的公开入口 `ds-superagent/postgres-storage` 提供 `PostgresStorage.open(options)`，实现与 SQLite 相同的 `Storage`/`AsyncTx` 合约：`get`、`insert`、`replace`、`remove`、`list`、`scan` 与 `transaction(instanceId, operation)`。它可接受 `connectionString`，也可接受 `host/port/user/password/database/ssl`；默认只按显式配置连接，不发现或写入用户自有 DSH 数据。
- schema 由版本表 `ds_superagent_meta(key, value)`（`schema_version=1`）、Instance 协调表 `ds_superagent_instances(instance_id)` 和记录表 `ds_superagent_records(instance_id, kind, id, body jsonb, seq identity, PK(instance_id, kind, id))` 组成。`list` 按插入序号 `seq` 返回，`scan` 按 `id` 游标返回，保持与 SQLite 后端一致的查询语义；记录体上限 128 KiB，查询上限 101。
- 事务固定锁序：先 `INSERT … ON CONFLICT DO NOTHING` 保证 Instance 协调行存在，再 `BEGIN ISOLATION LEVEL READ COMMITTED`，`SET LOCAL lock_timeout/statement_timeout`，随后 `SELECT … FOR UPDATE` 锁同一 Instance 的协调行，最后才读回执/状态并写记录。同一 Instance 因而串行，不同 Instance 互不阻塞；首次并发命令收敛到同一协调行。
- 预算是声明并可配置的：`maxConnections` 默认 8（1–64），`lockTimeoutMs` 默认 1500（1–60000），`statementTimeoutMs` 默认 4000（1–60000）。命令级重试上限沿用 `commandTransaction` 的 3 次尝试；`SERIALIZATION_FAILURE`/`DEADLOCK` 整事务重跑，`COMMIT_UNKNOWN` 先断开旧连接、用新连接重新加锁查原 `commandId`。隔离级别固定为 `READ COMMITTED`；初始化和首次协调行插入前显式 SET 连接预算，连接串 `options` 无法覆盖。
- 错误映射：PostgreSQL `40001` → `SERIALIZATION_FAILURE`，`40P01` → `DEADLOCK`，`55P03` → `LOCK_TIMEOUT`，`57014` → `STATEMENT_TIMEOUT`，`23505` → `RECORD_EXISTS`，包括服务器明确返回的 COMMIT 错误；只有结果无法查证的连接失败保留 `COMMIT_UNKNOWN`，连接建立失败为 `STORAGE_UNAVAILABLE`。`55P03` 不会被伪报成接单成功。
- 事务内只做数据库读写，不执行外部副作用。COMMIT 应答丢失后，`commandTransaction` 在新连接的 Instance 锁下按原 `commandId` 查回执；已有回执则返回同一结果，不重复写 Event。同 ID 不同 fingerprint 仍按既有命令身份规则拒绝。
- schema 初始化/升级：已有版本表时校验版本必须为 1 且 records/instances 表齐全，版本过新或缺表一律 `UNSUPPORTED_SCHEMA` 且不写数据；只有 records 表而没有版本表视为孤儿 schema，同样拒绝。旧版 `records(instance_id, kind, id, body text)` 必须提供绝对 `backupDirectory`，先写出并回读校验 JSON 备份，再在同一事务内建新表、复制数据、把旧表改名为 `ds_superagent_legacy_records` 并写入版本；任一步失败整体回滚，旧表与数据保持原样。并发的首次初始化由 `pg_advisory_xact_lock` 收敛。
- `superagent/scripts/build.mjs` 增加 `postgres-storage` 构建入口，`package.json` 暴露对应 export。`commands` 构建产物用于后端重试集成验证，不增加 package export。新依赖固定为 `pg@8.23.1`、`@types/pg@8.23.1`、`embedded-postgres@17.11.0-beta.19`。

## 审查后补强与故障证据

- PostgreSQL 专项最终 **22/22**，包括连接串预算覆盖负例。事务 capability 在 commit/rollback 前失效，保留的 `AsyncTx` 不能再操作已归还的 PoolClient；scan 的比较和排序使用 `COLLATE "C"`，保持 SQLite 字节序分页语义。
- 每次打开在 advisory 事务锁内核验表列、类型、非空性、identity 与主键顺序；缺列、错误类型、缺主键即拒绝。旧表还核验四个 text NOT NULL 列；迁移先持有 ACCESS EXCLUSIVE 表锁，备份与复制读取同一静止数据，备份文件使用独占创建、sync、完整字节回读比较。
- 升级在创建 meta、instances、records 及旧表 rename 四个 DDL 窗口分别通过 PostgreSQL event trigger 终止自身 backend。每次均确认旧表和数据仍在、版本未出现、备份已落盘，移除注入后可重新升级；另外测试迁移 COMMIT 前断开与 COMMIT 后丢应答，重新打开均可读到原记录。
- 备份恢复在另一独立数据库重建旧表、导入备份、再次升级，再用公开 Storage 查询原回执；验证的是业务记录恢复。未声称保留旧库权限、索引、Session 或外部副作用。
- 真实死锁由两个不同 Instance 的 PostgresStorage 事务通过测试触发器反序锁定行产生；命令事务一个执行一次、另一个完整执行两次，证明真实 40P01 经过后端分类与 `commandTransaction` 重跑。原始 SQL 死锁与假 storage 重试测试仍作为补充。
- 延迟约束触发器在 COMMIT 时分别返回 40001 和 23505，前者整事务两次成功，后者一次即 `RECORD_EXISTS`；不再把明确回滚误作 unknown。语句超时触发器验证 100 ms 预算，40001 注入验证恰好三次即 `RETRY_EXHAUSTED` 且不留下记录。
- 公开 Engine 验证同 ID 异文 `IDENTITY_CONFLICT`；公开 Effects 验证 success/transient/defer/permanent 四类旧结果不能覆盖新 payload/generation。
- 声明负载为 32 个并行命令、4 个 Instance、4 条连接：Windows Node 25.4.0 专项最终样本总 258.7 ms，p50 31.7 ms、p95 227.3 ms、max 255.8 ms；默认锁 1500 ms、语句 4000 ms、最多 3 次在本样本有余量。连接建立或池等待预算为 5000 ms，首次协调行建立和初始化也受连接级锁/语句预算约束。这是本机开发样本，不是生产 SLA；尝试预算限制次数，并不为任意用户回调提供总耗时保证。
- Node 24.22.2 最终相关文件样本：同样负载总 134.7 ms，p50 19.4 ms、p95 97.0 ms、max 132.6 ms；后续部署仍须在实际负载下复核预算。

## 边界

- embedded PostgreSQL 只是测试用的真实本地隔离实例，不是生产部署证据；生产数据库连接、备份目的地与运维仍由操作者提供。
- 未覆盖复制、failover、掉电持久性、TLS/证书、连接池调优与网络分区下的全部故障形态；本票只验证声明预算内的锁等待、语句超时、串行化/死锁重试与 COMMIT 应答丢失。
- T42 只实现业务库后端，不实现 T43 的 Session 共享后端；Session 持久化仍按 T15/T43 分别验收。切换业务库也不会回滚已完成的外部副作用，不能把业务库恢复冒充 Session 或外部世界回滚。
- schema 版本仅支持 1；未来的 schema/命令扩展必须同步维护该后端与契约，过新版本明确拒绝而不是猜测迁移。
- 旧表升级要求显式绝对备份目录；不提供自动不可逆迁移，也不在没有可验证备份时改写数据。
