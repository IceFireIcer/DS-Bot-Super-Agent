# T34：确认远端 PTY 与进程树真正停止

- Issue：[T34 / #62](https://github.com/IceFireIcer/DS-SuperAgent/issues/62)。
- 实施基线：T33 提交 `6bc6e99`。

## 已交付

- 设备命令可声明 `pty: true`。PTY 由真实 `node-pty` 分配，设备新增 `terminal.write`、`terminal.resize`、`terminal.signal`，启动仍使用同一作业 ID、Instance/Environment/incarnation 校验和持久作业记录。
- Host 的 `RemoteSubprocess.spawnTerminal({ name, rows, cols, terminalType? })` 返回公开 `RemoteTerminalHandle`：`pid`、`output` 可读流、`done`、`write()`、`resize()`、`inspectForeground()`、`inspectActivity()`、`terminate()`。设备支持真实字节流、写入和尺寸变更；`inspectForeground` 返回 `undefined`、活动状态返回 `unknown`，`signalForeground` 明确返回 `UNSUPPORTED_CAPABILITY`，不伪造前台进程组语义。终端 live 输出同样经过 secret/root sanitize。
- 普通命令在 POSIX 上以独立进程组启动；取消向整个进程组发送 `SIGTERM`，250 ms 后升级 `SIGKILL`。PTY 同样按会话/进程组停止。Windows 使用 `taskkill /T /F`；ConPTY 报 `pid = 0` 时只终止终端本身，明确声明该平台进程树证明弱于 POSIX。
- 设备作业区分 top-level exit 与 managed range quiet：`exited` 表示根进程已退出，`settled` 只在同一进程组实际为空时才为 true。`done` 可在根进程退出时返回，`waitForExit` 只有 `settled` 且状态为 `exited`/`cancelled` 才返回 true。仅结束父进程、仅取消 Host promise 或只收到 terminal exit 都不会被报告为远端 `cancelled`。
- `StopState` 新增 `pendingDeviceConfirmation`。停止远端 Assignment 或有远端 job 时先持久 `stopping` 和 pending；`confirmStop` 在 pending 未由设备范围证据清除前拒绝写 `stopped/cancellationConfirmedAt`。离线停止仍立即写入 Ticket stopped constraint，后续跟进、恢复和设备回连不能解除；subagent/child 结束不算 managed range 证据，只有每个远端 job range confirmed 才清除 pending。
- `RemoteBoundEnvironment.inspectRange(jobId)` / `cancelRange(jobId)` 按原 job ID 查询和取消设备范围；`Engine.reconcileStop({ commandId, ticketId })` 重连后只接受 `settled` 的 `exited`/`cancelled` 快照并清除 pending。再次取消仍在运行的同一范围，不启动新作业。
- 子代理工具不再限制在 local Environment：远端 Assignment 的子代理继承父 Worker 的远端文件/命令工具，`run_command` 通过同一个 bound Environment 执行；父 stop 中止子 Session/信号，远端范围由同一 job/Environment 归属取消，迟到结果不会创建新执行。T34 没有新增子代理专用的 PTY/JOB 工具。

- `test/remote-stop.test.mjs`：远端长作业在传输中断期间 stop，状态保持 `stopping`、`pendingDeviceConfirmation = true`，job 为 `unknown`；恢复仍被 `STOPPING` 拒绝，不伪报 cancelled。
- `test/remote-command.test.mjs` 新增 direct range 测试：原 job ID 的 `inspectRange` 观察到 `running`，`cancelRange` 后只有 `settled` 的 `cancelled` 才确认。
- Windows Node 25.4.0：全量 **287/287**，typecheck、lint 通过；PTY/进程组测试在本机 Windows 上通过（Windows 平台边界按上文声明）。

## 边界

- Windows ConPTY 不提供可用 top-level PID，进程树终止是 `taskkill /T` 最佳努力，不是 Job Object 级证明；POSIX 进程组证明不覆盖主动 `setsid`/双 fork 脱离组的后代。
- `spawnTerminal` 只接受设备配置名和尺寸，不接受公开 `SubprocessTerminalSpawnSpec` 的任意 argv/cwd/env/graceMs；`signalForeground` 未验证，明确拒绝。这是 T34 的受限 provider 子集，不是完整 DSH runtime 认证。
- 真实第二设备验收覆盖 PTY、进程组与终止确认；断连 stop 和迟到结果目前由 loopback 测试覆盖，没有在这台真实 Linux 设备上重新演练。
- 远端前台 `run_command` 仍是同步调用，没有持久 JobRecord；离线 stop 的前台范围只能由 Worker abort/设备回连核对，不能按 job ID 单独查回执。这留给 T35 的恢复对账。
- `inspectForeground` 和终端活动状态没有设备侧可靠实现，明确返回 `undefined`/`unknown`，不把未知当 idle。
- daemon 崩溃、跨 Host 接管、多分钟断连和长期租约竞争仍属于 T35；T34 已持久 stop/pending 和原 job ID 查询，不把 T35 的日志恢复冒充活进程恢复。
- T34 代码与真实第二设备 PTY/进程组验收完成；GitHub issue 仍为 open，等待推送、合入与发布。
