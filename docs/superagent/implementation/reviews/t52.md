# T52 双轴审查

- 基线：`464b9df`；主代理并行 Standards/Spec 复核，修复后重跑定向、真实进程、全量与类型/lint。

## Standards

- **修复：** `detach(batch)` 不再 `void batch`，改为校验 batch 标识；删除了未使用的参数语义。
- **修复：** activation identity 的重复字面量收敛为 `CURRENT_CORE`/`CurrentCore`；测试中 release 断言改为直接找 `state === 'released'` 的 ledger，并核对原 gap input。
- **修复：** activation replay 不再无条件要求旧 snapshot adapter；只有真正未激活路径才要求 `legacy`。
- **修复：** activation 子进程 fixture 的退出码改为命名常量；测试 cleanup 先关闭 storage 再删除隔离目录，避免 Windows EPERM。
- **保留判断：** `releasePending` 仍较长，包含 claim/settle/counts 三段；它对应一个持久 release ledger 生命周期，拆分会让同一事务边界的读取分散。T53 需要扩展逆向交接时再拆。
- **保留判断：** `receiveSource`/`assessSourceBatch` 的 gate 预检和后续命令事务是两次读；当前 gate 只做只读 manifest/lease 校验，命令事务内部仍校验 accept/Effect 写入。T53 若把 gate 事件化再合并。
- **保留判断：** activation 测试与 T51 fixture 有重复的端口/legacy helper；两个票的演练边界不同，当前共享测试 helper 会引入跨票耦合。

## Spec

- **修复（阻断）：** 插件未安装 activation gate。`Config.activationGate` 现在由 `apply` 安装到 Engine；新增插件 gate 回归。
- **修复（阻断）：** release 只更新 `activation-gap`，T51 gap input 仍显示 held。成功释放现在同一事务把 `switchover-gap-input` 标为 `released`、`released-to-current-entry`，`GapCounts` 增加 released，T51 状态与 activation ledger 一致。
- **修复（阻断）：** gate 只校验 epoch/expiry，不校验 lease owner。现在要求 `host-lease.owner` 等于当前进程 token；真实退出演练中父进程的 `releasePending` 被拒绝，证明第二进程不能重复派活。
- **修复：** 同 batch/epoch 但新 command ID 的 replay 未写 activation 回执。现在写入 `activation-command`，测试查询该回执；同 ID 异 fingerprint 拒绝。
- **修复：** activation 使用 heartbeat 会改写的 `updatedAt` 做 stale CAS，可能误判。改为比较 state/blockers/checkpoints 与最终 recheck 的 gap 计数。
- **修复：** release 丢应答后同一调用会立刻重试，unknown 不可见。现在每次调用每个 ledger 至多尝试一次，unknown 留待下次 `releasePending`；同 command 重试不重复 Ticket。
- **保留（边界）：** activation 必须与 T51 gap holder 同进程；跨进程 holder 接管和真实旧服务自启动适配留给 T53/T55。
- **保留（边界）：** 真实退出只覆盖 activation 提交/外部接受后子进程退出与 owner 拒绝；跨 epoch 恢复和逆向交接留给 T53。
- **保留（边界）：** “真实应用隔离目录”是临时隔离目录 + 真实旧进程 + SQLite + mock 新 Session，不是 Electron 安装包/真实产品旧团队；用户数据迁移未运行且需单独授权。

## 结论

- Standards：0 hard violation；剩余判断是 `releasePending` 长度、双事务 gate 与测试 helper 重复。
- Spec：activation gate 默认安装、gap released 双账本、lease owner、command 回执与 unknown 可见性均已修复；跨进程/真实应用边界明确留给 T53/T55。
