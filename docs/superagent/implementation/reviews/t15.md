## Standards

首轮指出硬问题：`superagent/README.md` 的 T02 预览段仍写着 SQLite Session 持久化“留给 T15–T20”，与新增章节矛盾；README 把导出子路径写成 `superagent/session-persistence`，实际包名是 `ds-superagent`；`session-persistence.ts` 有三处描述代码本身的注释；错误参数用裸 `TypeError` 而兄弟模块用带码 `CoreError`；证据链接 `reviews/t15.md` 尚未创建。

实现改为：更新预览段，说明 SQLite Session 持久化已由 T15 提供、浏览器预览仍用 JSONL；修正导出子路径与包名；删除冗余注释；补齐本审查记录。`TypeError` 保留在公开 DSH 参数校验处，因为 DSH 自身的 `materializeCreateHeader`/`materializeAppendBatch` 同样以 `TypeError` 表达非法参数，这里是契约一致而不是本仓库 `CoreError` 的替代。

判断项：`meta()`/`open()` 的头校验重复、`close()` 与 `assertWriter()` 的 writer 判定重复、`events()`/`list()` 的分页循环重复、两份测试的失败注入包装重复。实现抽出 `readMeta`/`requireMeta`、`readEvents`、`readWriter`/`assertActiveWriter` 与 `runtimeWithFailureInjection` 测试 helper。`StoredWriter.closedAt` 未被任何路径读取，按“避免投机性抽象”删除；`owner` 最初也只是写入而未读取，复审期间因崩溃恢复需要被赋予明确语义（owner PID 存活探测），予以保留。`instanceId` 更名为 `storeNamespace`，说明它是存储命名空间而不是 Engine 实例。`SqliteSessionHandle` 仍同时承担 handle 契约、校验与 live 队列；在本票规模下拆分会增加跨对象状态，暂不拆分，后续若 schema 与生命周期继续增长再评估。

## Spec

AC1：provider 用公开 `SessionPersistence`/`SessionHandle` 实现，事件键按补零 seq 排序，`assertContiguous` 拒绝非连续批次，头由 `assertVersion`/`assertStoredId` 校验，读回由 `validateStoredEvents` 校完整段日志；`open(id,'write')` 在授予写权前先校验既有日志，损坏或未知事件类型的日志被拒绝。fork 通过 `create(header,{inheritedEventCount})` 保留 `parentSession`、`isSeeded` 与继承 cut。原生 loop 通过 `session/event`、`session/flush`、`session/disposed` 接入。

AC2：构造/恢复记录（`session/end-seed`、interrupted closers）由 loop 在 `prepared.publish()` 前经 `appendUnstoredSuffix` 写入。provider 的 `append` 每次即持久提交，因此没有待刷新缓冲，等价并强于“flush 后再 announce”；写入失败会让 `appendUnstoredSuffix` 抛错，广播不会发生。测试覆盖：种子 Session 在 `session/created` 时已能读到构造记录且 seq 与 seed 一致；构造后缀持久失败时 `session/created` 不触发；setup 发布前失败时无残留；恢复未关闭回合时在公告前补存合成 closer。

AC3：`append`/`flush`/`close` 均在同一事务重读 writer 行并比对 epoch 与活动标志；注入 flush/close 持久失败仍保有写权且可继续写入；epoch 被推进后旧 handle 三个写操作全部抛 `SessionOwnershipLostError` 且不重获；服务级 `flush()` 失败用 `AggregateError` 报告且不释放任一 writer。旧 handle 在被替换后只报已关闭行为，不静默写回。另有真实子进程崩溃测试：子进程写入后直接退出，父进程探测到死 PID 才以新 epoch 接管；活进程或同进程第二实例仍被拒绝。PID 被无关进程复用是已知局限，记录在验收文档边界中。

AC4：真实公开生命周期测试覆盖并发交错（两个 Session 各四次交错 append 后 seq 连续）、取消（保留可恢复历史与恢复标记）、恢复（替换适配器后 resume 同一 Worker，历史连续）、fork（真实 `ctx.sessions.fork` 的 DSH 血缘与继承前缀）、服务替换（第二后端拒绝活动 writer；第一后端释放后续写并读到既有事件）。报告分开：业务事实仍由既有 store 记录，Session 日志由本 provider 记录，二者共用事务工作线程但独立查询与校验。

规格评审首轮另指出两处实现问题，均已修复并加测：create 立即写 meta 会在发布前失败时留下空 Session，现改为 close 时删除未 append 的创建记录；`open('write')` 原先只校验头，现补校验日志。未发现范围蔓延。

复审在第一轮修复后的工作树上继续指出并已修复：

- 空 Session 删除条件过宽：显式 `flush()` 过的空 Session 也被删除，违反公开 `SessionHandle` 契约。现以 handle 的 `materialized` 标志区分“从未物化”和“已 flush”，只有前者在 close 时删除，并加测 `flush` 后关闭仍可重开。
- `close()` 并发调用不幂等：两个并发 close 都在 `closed` 检查后进入事务，第二个会看到 `active: false` 并抛 `SessionOwnershipLostError`。现用共享 `closing` promise 合并并发调用，失败后清除以便重试，加测三个并发 close 只结算一次。
- 日志校验不完整：`validateStoredEvents` 只校验事件类型，不校验序号连续和事件数与头游标一致。现在 `readEvents` 同时核对 `eventCount === nextSeq` 与从 0 开始的连续性，损坏时抛 `SessionPersistenceCorruptionError`，并加缺口测试。
- live append 失败后继续排队：原实现把错误存进 `liveError` 后仍继续处理后续事件，最终 flush 只报第一个错误。现在首个失败后 handle 停止接收 live 事件，后续 append/flush/close 都报原始失败；加测存储前缀保持连续且无静默丢事件。
- `StoredWriter` 仍有未用字段且 owner 以字符串再解析。现在记录改为显式 `pid: number`，`sessionId` 用于行身份校验，删除未用的 `openedAt`；`assertActiveWriter` 同时核对行归属。

规格复审另质疑 AC2 的“flush 后再 announce”证据。实现说明：provider 的 `append` 与头游标在同一事务提交，本身即持久 checkpoint，没有可被跳过或丢失的缓冲；因此构造后缀的 `appendUnstoredSuffix` 返回时已越过 flush 屏障，失败会直接阻止 `publish()`。新增中途失败原子性测试（无部分事件、可整批重试）与发布前持久失败测试，分别证明“append 应答不是半提交”和“屏障失败不公告”。旧 handle 的 epoch 失效无法在单进程内由公开生命周界自然产生（只能来自崩溃接管的持久行），故保留对崩溃恢复行的模拟测试，并以真实子进程崩溃接管测试补强。
