# T12 双轴审查

- 日期：2026-11-08。
- 固定基线：`bea20f1`；审查目标：T12 提交前工作树，对应实现提交：本票提交。
- 范围：持久后台 job（启动事实、有界输出、退出查询、取消与归属）、回合结束后仍持槽、完成事件回原 Worker 与迟到完成隔离、按归属清理与声明等待、`acceptSource` 的显式 Environment 绑定、同源 chat 入口，以及真实 Windows 长命令实测。

## Standards

首轮指出一处硬违规和若干正确性缺陷。硬违规：`superagent/README.md` 仍写 "async jobs … are rejected"，且 "Concurrent Worker slots" 说槽在 idle/ready 时释放，与新的 `worker-jobs` 持槽矛盾，同时没有记录 T12 的新公开面（`jobs` 选项、`listJobs`/`getJob`/`cancelJob`、`Engine.shutdown`、`Jobs` 导出、三个 chat 路由、`start_command`/`job_status`/`cancel_job`、`worker-jobs`、`SlotActivation 'job'`、`backgroundTimeoutMs`、`acceptSource({ environmentId })`）。

正确性缺陷：settlement 写库失败后注释声称“下次读取会核对”，但同 runtime 的 running 记录永远不会被核对，槽会永久泄漏；`stopTicket` 用 `{ id: '' } as Assignment` 伪造 Assignment，使 `confirmStop` 匹配不到而让 Assignment 停在 `stopping` 却显示 `stopped`；`Jobs.start` 在调用方事务内改内存状态、且进程先于 `JOB_BUDGET` 检查 spawn；模型侧取消记为 `human`，与人工命令混同。

实现改为：`Jobs` 拆成 `assertCapacity`（spawn 前检查）、`start`（只写记录并暂存 handle）、`attach`（提交后开始观察）与 `abandon`（未提交则终止进程且不留 handle/timer）；`confirmStop` 改为接受 `assignmentId` 而非伪造对象；模型取消记为 `worker`，`wakeForJob` 对 `human`/`worker` 都不唤醒；README 按 T11 的写法补上 T12 章节并改正两处旧表述。其余气味（`hasPendingInTransaction` 是 effects 里第七份分页扫描、`chat-server` 的三元链、`worker()` 五个位置参数）保留现状：各自与既有同模块写法一致，改动会把本票扩散到无关文件；`JobState 'failed'` 已删除。

## Spec

首轮确认 AC1/AC2/AC3 的主干与 T11 槽预算、人工优先、无饥饿保证均未被破坏，但指出四处实质问题：job 完成是否占用人工额外槽缺证据；`README.md` 与 `docs/superagent/implementation/README.md` 的 `reviews/t12.md` 缺项；清理只覆盖活动 job，长寿命 Ticket 累积约 1000 条 job 记录后 `conversation()`/`listJobs()` 会永久报 `JOB_BUDGET`；`Jobs.cancel` 在进程范围静止前就写 `cancelled`，与 D14 “只有确认同一 managed range 实际静止后才报告 cancelled” 冲突；`stopRanges` 对没有 handle 的 id 静默当作已确认。`stopTicket` 对 `running` 的重新定义与 `acceptSource({ environmentId })` 属跨票改动，已在验收记录中单列说明。

实现改为：新增 `cancelling` 中间态，`cancelled` 只在 `stopRanges` 观察到范围为空后写入，并在丢弃 handle 前读取有界输出尾部；无法观察时写 `unknown`（`markUnconfirmed`），与"不可证明的本地执行"在全规格中的表示一致；`stopRanges` 只返回真正观察到空范围、且由本 runtime 持有的记录，`stopTicket` 只有在全部 id 都确认时才提前落下取消确认；`worker-jobs` 的收尾改为幂等核对（无活动回合、无活动 job、无排队 relay 时才释放槽）。补充测试：`Slots` 契约上验证 `activation: 'job'` 在正常预算满时排队而不占用额外槽（引擎侧 job 完成复用本票自己的槽，属正确行为，故不在集成层断言排队）。

复审第二轮进一步指出：`stopRanges` 先丢 handle 再读输出导致取消记录没有输出（已改为先读后放）；并发启动可同时通过预算检查（改为在 `start` 事务内检查）；自动裁剪 settled 记录违反审计"本规格保留原始证据，不擅自增加自动清理"（已撤销自动删除，改单票查询有界为最新 100 条，记录保留）；本 runtime 的结算写库失败会留下永不核对的 running 记录（`reconcile` 改为：本 runtime 但无 handle/pending 的记录同样读作 `unknown`）；`JobState 'starting'` 从未写入（已删除）、`maxPerAssignment` 名称易混（改为 `maxPerTicket`）；`implementation/README.md` 计数不一致（已同步）。

## 证据

第四、五轮复审又修入三处：`stopRanges` 在确认事务提交前保持对 job 的 claim，且 `settle` 的自然退出不会清掉在途取消的 claim，`finishStopped` 全部放进 `finally`（否则一次写库失败会让 `cancelling` 永久持槽、或让已确认的停止被并发读取降级为 `unknown`）；取消路径与 `cancel_job` 工具都保留确认时读到的有界输出；活动 job 改用 `job-active` 索引判断，历史超过查询预算也不会隐藏仍在运行的工作（测试用 120 条历史记录加一个活动 job 验证）。文档同步为 142/142，并把"超额启动"的表述改为"不留下 record 或 handle"（进程会先创建再终止）。

`npm run typecheck`、`npm test`（142/142，连续三轮）、`npm run lint`、`node dev/jobs.mjs` 与 `node dev/slots.mjs` 均通过，见 [T12 验收记录](../t12.md)。
