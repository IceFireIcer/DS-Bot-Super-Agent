## Standards

首轮指出：`Effects.start()` 用未跟踪的 IIFE 启动扫描，`drain()`/`stop()` 可能在扫描完成前派发或关闭存储；为测试新增了生产方法 `Engine.recoverInputs`；恢复 effect 用 `randomUUID` 强制新载荷，绕过 enqueue 的幂等；`pendingInputs` 扫描全部历史 `work-input`，超过 1,000 条会让恢复整体失败；`reviews/t16.md` 缺失；所谓 flush 失败是替换 `SessionStore.flush`，不是 Session provider 的真实失败。

实现改为：启动扫描作为 `passes` 中的 promise，`drain()` 先等待 `ready`，`stop()` 等待所有 pass；移除 `Engine.recoverInputs`，测试改走 `effects.start()` 的真实启动契约；恢复载荷使用确定性的恢复次数；新增可分页的 `pending-input` 索引并在完成/耗尽时移除；fixture 继承真实 SQLite provider 并让写 handle 的 `flush` 抛出注入失败；补齐本记录。`TypeError` 保留在公开 DSH 参数校验处，与 DSH 自身契约一致。

第二轮继续指出：恢复说明只检查原 messageId，恢复回合崩溃后会再追加一条相同说明；>1,000 个 pending 仍会失败；`Engine.recoverInputs` 仍被 README/验收记录称为公开 API；扫描失败被静默吞掉；exhaustion 逻辑重复；文档声称检查了 Assignment 状态但代码只查 Ticket。实现改为：恢复说明带尝试序号、每次使用新 messageId；pending 索引逐页读取且单项失败只警告；文档移除不存在的 API；恢复上限与 exhaustion helper 统一；文档改为只声明实际检查的 Ticket/constraint 与 ownership。

判断项：`InputDelivery` 同时保存原消息、恢复消息与最近持久消息 ID，属于有语义的三元事实而不是重复字段；`attempts` 与 `recoveryAttempts` 分别限制总投递和恢复回合，均被读取。`claimDelivery` 改为展开旧 delivery 保留全部可选字段，避免新增字段被静默丢弃。

## Spec

AC1：`claimedAt`（claim）、`sentAt`（交给适配器）、`persistedAt`/`persistedMessageId`/`persistedSeq`（flush 后的持久历史）、`completedAt`/`outcome`（工作承接）分开保存。`report_ready`、`ask_human`、`handback_input` 在各自验收事务内完成 Input，消除“已验收但 Input 仍 pending”的崩溃窗口。`NativeSessions` 只有在观察到对应 `session/event` 并成功 `sessions.flush()` 后才回调持久回执；发送前等待 append 或超时，不再用可能提前完成的 `whenIdle`。

AC2：`messageId` 由 Input ID 确定性派生并在首次 claim 时持久化。未入历史的重发使用同一 ID；已入历史的不再追加原用户消息，改用带尝试序号的恢复说明。恢复说明每次使用不同的确定性 ID，避免“相同用户消息反复追加”。relay 的 `reconcile` 重新执行未知回合，但 Worker 先读持久边界，因此只会续传。

AC3：idle 回合只写 `persistedAt`，不写 `completedAt`，Input 保持 `pending`；重启扫描发送恢复说明后，只有真正 ready/waiting-human/handback 才转 `delivered`。handed-back / requeued 的 ownership 不会被恢复扫描重新 attach。重试保留 Ticket 与 Session，但创建新的 Assignment 代次，符合 D09 的“保留 Session、创建新 Assignment”；原生 inbox 是进程内状态，崩溃重启后没有旧副本可清理，原消息只在持久历史中出现一次。

AC4：五个真实隔离子进程退出窗口均有测试：claim 前、claim 后/append 前、append 后、provider flush 注入失败后、持久回执后；重开后检查 Input 的 claim/sent/persisted 边界、Session 中用户消息数量、ownership 状态以及最终交付。另有进程内 idle + 重启和 handed-back 不重投测试。恢复扫描逐页处理、单项失败不中止整轮，恢复与总投递都有上限。

CI 的 Linux Node 22.19/24 运行暴露了一个既有缺陷：`SourceEvaluations.runNext` 直接把 `eval` 扫描页的值当成评估记录读取 `id`，遇到无 `id` 的 `head:` 行会抛错，导致 after-claim 的 turn 在 claim 后静默中断。修复为按扫描条目的 key 前缀过滤后再读取值；该修复是恢复测试能稳定通过的前提，不扩大 T16 行为。after-claim 夹具也改为独立轮询持久 claim、一观察到 `claimedAt` 就退出，避免依赖 turn 启动时机。
