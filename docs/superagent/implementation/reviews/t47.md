# T47 双轴审查

- 基线：`966f5c5`；主代理按 Standards 与 Spec 两轴并行复核，修复后重新运行定向、全量和 Windows 演练。

## Standards

- **修复：** `ProcessWatchdogHost.stop()` 在 `this.child === undefined` 时直接返回 `stopped`，与 README 的“不是本适配器启动的 Host 报 timeout”冲突。现在先读状态文件：PID 仍存活就返回 `timeout`，不会在该 Host 还活着时启动第二个 Router；新增“未启动但存活”的进程测试。
- **修复：** `Watchdog.restart()` 只给适配器的 abort 设了计时器，却直接 `await host.stop()`；适配器忽略 abort 时巡检会挂住。现在用 `withTimeout` 给 stop 也加硬上限，超时记录 `restart-timeout`；新增“stop 永不返回”的测试。
- **修复：** `graceMs` 允许到 30 分钟，违反 D16 的“最多等五分钟”。上限收为 300,000 ms，默认同为五分钟；新增构造器拒绝 300,001 ms 的测试。
- **修复：** `restart-timeout` / `restart-failed` 沿用 service-failure 的 fingerprint，变化后的重启错误会被当成未变化而静默。两种结果现在各自生成带 detail/after 观察的 fingerprint；新增“A 错→B 错→B 错”的通知去重测试。
- **修复：** `notify` 抛错时 `deliver()` 返回 `suppressed`，把“没有送达”伪装成“已经通知过”。现在返回 `failed`，不写 dedupe key，下次继续尝试；新增通知失败重试测试。
- **修复：** `watchdog-process.ts` 的 `log` 选项从未读取。删除。
- **修复：** 审查发现的 `t47-acceptance.out` 含用户临时目录，未提交；提交前删除。T47 缺少 `t47.md`/`reviews/t47.md` 的流程缺口已补。
- **修复：** Windows 全量测试中 `watchdog-process.test` 清理临时 SQLite 时报 `EBUSY`，因为 `dispose()` 只发 SIGKILL 不等退出。`dispose()` 改为等待子进程退出（最多 5 s），测试与演练 `await` 它。
- **保留判断：** `Watchdog` 仍是约 400 行的单一模块，包含配置、分类、重启、通知和持久化。状态机、预算和去重共享同一份事实；拆成分类器/存储/文案三个模块会把一次巡检拆散在多个文件，当前保持一个可审计入口。
- **保留判断：** optional field 的 `...(value === undefined ? {} : { value })` 和来源/组件过滤重复出现。它们服务于 `exactOptionalPropertyTypes` 和可读的观察对象；没有引入通用 spread helper 去遮蔽类型。
- **保留判断：** `WatchdogKind` 的文案/升级/清 dedupe 仍用 if 分支而非表。三种“恢复成功/健康/正常等待”清 dedupe、四种通知升级，分支与 `WatchdogInspection` 字段一起变化；表驱动会把同一条规则拆到两个地方。
- **保留判断：** 验收脚本和进程测试都有 `gone()` 小循环。两个文件运行在不同生命周期里，当前不为了十几行抽共享测试模块。

## Spec

- **修复（阻断）：** T47 要求“独立 profile/进程默认每小时检查”，原实现只有库和演练，没有可部署入口。新增 `ds-superagent-watchdog` CLI 与 pid/status/IPC 适配器，默认 3600000 ms；CLI 作为独立进程启动并重启真实 Host 的测试通过。
- **修复（阻断）：** T47 要求“后两者不重启 Host”，原分类先看 `service === 'failed'`，会带着 setup/组件错误也重启。分类顺序改为组件 → setup → 服务；新增“service failed + setup missing / source failed 不调用 stop/start”的测试。
- **修复（阻断）：** D16 要求每次干预保存观察、依据、动作、结果、版本和预算。`WatchdogInspection` 新增完整 `observation` 与重启后的 `after`；`watchdog-state` 保存它们。验收报告包含 observation/after/version/budget。
- **修复：** 五分钟上限、stop 硬超时、changed-error fingerprint、通知失败重试均如上；这些直接对应 D16/A24。
- **修复：** 验收 Host 原先没有原生运行时，takeover 只能走 `completeTakeoverWithoutRuntime()`（结果固定 `blocked`）。演练 Host 现在挂 `NativeSessions` + mock 模型，并 seed 一个带 Session 的 running Assignment；两轮真实演练的 `takeover.outcome` 为 `resumed`，走的是 `Engine.acquireHost()` 的 Execution takeover，而不是无运行时兜底。
- **保留（边界）：** 真实设备/远端 job 的对账证据仍由 T44 的两进程 Windows→Ubuntu 验收承担；T47 的 Watchdog 只调用同一个 `acquireHost()` 入口，没有伪造第二个远端设备。记录中明确分开。
- **保留（边界）：** “托管配方”是同一台 Windows 上的 embedded PostgreSQL 共享业务后端，不是远程服务器。远程托管、网络分区和跨机 Watchdog 未运行；记录中明确。
- **保留（边界）：** 没有控制 OS 睡眠/关机；T47 是服务恢复，宿主睡眠边界属于 T46。
- **保留（边界）：** 没有 Windows Service/计划任务注册、日志轮转或开机自启；CLI 是独立进程入口，部署形态留给 T55。
- **保留（边界）：** Watchdog 是单实例假设；同一 Instance 的两个 Watchdog 会竞争同一 `watchdog-state` 记录，当前没有额外协调锁。记录中明确部署应只启用一个。
- **保留（边界）：** 通知只调用调用方 `notify`；CLI 输出 stderr。没有真实飞书/GitHub/桌面通道，也没有跨小时外部通知重试。
- **保留（边界）：** 语义监督（无效循环、目标偏离、纠偏/暂停提案）是 T48；T47 只做服务分类与恢复，不判断工作质量、不修改配置。
