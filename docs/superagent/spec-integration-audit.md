## 一致性处理

1. 将方案区统一为纯本地、本地控制远端、服务器托管三种部署/执行关系。工具执行切换不等于 Host、模型端点或两类存储迁移；本机休眠不承诺持续执行。
2. 跨信道交付整合原默认回发起处与后续已确认的目标更新：有可核查、可访问且获授权的跟进，才能记录交付目标变化；新事件不自行触发改投或广播。
3. 区分 Ticket/Assignment 生命周期、Report 和用户可见状态。人工 stop 立即取消继续执行授权，设备停止仍可 pending；结束执行安排不证明设备已静止。
4. 跟进复用当前工作与会话归属，但合法 Session 换代、Assignment 恢复和自然结束后恢复保留独立语义；不把“同一个 Worker”解释为永不替换 OS 进程。
5. Input claim、投递、进入持久 Session 历史与实际工作承接分开；flush 保证持久前缀，不能证明模型已处理或外部副作用恰好一次。
6. 将业务回调事务、Session 后端写权和设备作业隔离分别描述；权威链不被错误解释成跨三者的共同 ACID 事务，业务锁也不被当成进程停止证明。
7. 权限沿用明确动作授权、Policy/Mandate 与版本化规则；保留用户“参考原型机制”的选择，不新增动作分级配置界面。Watchdog 纠偏/暂停仍需明确批准。
8. 远端 scope/路径/作业协议并入行为契约，明确完整 spawn handle、Agent 继承、PTY/进程树、daemon 重启及生产认证仍待验收。
9. 移除“PostgreSQL/所有权决定仍开放”等失效进度句，保留 canonical resolution 链接与每项实验的证据边界；不修改旧决议以追求表面一致。
10. 去除词汇表中重复的 unknown 定义，将具体锁/代次实现保留在规格而非词汇定义中。网页原型未获用户体验验收，不能当作 UI 验收依据；状态取舍依据实际对话确认。

## 验证范围

本轮核验七个模板章节、用户故事 1—100、D01—D19、A01—A36 的连续性及引用、全部十二个正式决议链接和内容摘要、本地入口链接、无失效“仍阻塞”进度、实现决定中无具体实现路径或演示代码、发布前后 Issue 正文一致性与 ready-for-agent 标签。

这是文档完整性与追溯核查，不能证明生产行为正确；此前领域、SQLite、公共 DSH、同平台模拟和 PostgreSQL 的证据以规格矩阵为准，没有重新运行，不能称为本轮全绿。真实 DSH loop、完整后端、Windows、真实信道/模型及远端故障交接由后续实施验收。
